Zappy Server

AI Protocol

Source: server/src/protocol/ai/

The AI protocol module turns raw command lines into typed AiCommand values. It is a pure parser: it does not log, mutate state, or write to sockets. All decisions about what to do with a parsed command belong to handle_command.rs.

File structure

server/src/protocol/ai/
    mod.rs       module wiring and public exports
    command.rs   AiCommand enum
    error.rs     ParseError enum
    lexer.rs     Tokens cursor over the input string
    parse.rs     parse() entry point

Command names are case-sensitive. Forward is valid; forward is rejected with ParseError::UnknownCommand.

Connection handshake

Before a client is classified as Ai, it is Unknown. The first line it sends determines its type:

stateDiagram-v2
    [*] --> Unknown: TCP connected, WELCOME\n sent
    Unknown --> Gui: first line == "GRAPHIC"
    Unknown --> Ai: first line == valid team name with available slot
    Unknown --> [*]: team unknown / no slot / no egg
    Ai --> Ai: subsequent commands queued
    Gui --> Gui: GUI queries handled

On successful AI promotion, the server:

  1. Picks a random egg from the team.
  2. Spawns a Player at the egg's position.
  3. Registers the Token -> PlayerId mapping in State.
  4. Replies with remaining_slots\n then width height\n.
  5. Broadcasts pnw #id X Y O L team\n to all GUI clients.
  6. Broadcasts ebo #egg_id\n to all GUI clients (egg hatched).

Full team: When spawn_player_from_team_egg returns NoSlotsAvailable, the server sends 0\n then W H\n (zero slots + dimensions), flushes synchronously via flush_and_close, and disconnects the client.

Unknown team: The server sends ko\n and closes the connection immediately without sending slot count or dimensions.

Design patterns

LL(1) predictive parser

The parser is an LL(1) (Left-to-right, Leftmost derivation, 1-token lookahead) predictive parser. It reads one token (the command name) and immediately knows which branch to take. The Zappy AI grammar has no ambiguity and no recursion, so a flat match on the command name is sufficient.

flowchart TD
    INPUT["'Take food'"] --> LEXER["Tokens::next_str()"]
    LEXER --> CMD{"command name?"}
    CMD -->|"Forward"| FWD["Ok(AiCommand::Forward)"]
    CMD -->|"Take"| RES["Tokens::next_str() = food"]
    RES --> KIND{"ResourceKind?"}
    KIND -->|"food"| TAKE["Ok(AiCommand::Take(Food))"]
    KIND -->|"diamond"| ERR["Err(InvalidResource)"]
    CMD -->|"unknown"| UNK["Err(UnknownCommand)"]

Zero-copy cursor

The Tokens<'a> struct holds a &'a str slice that shrinks as tokens are consumed. Returned tokens are also &'a str slices borrowing from the original input. No String allocation occurs on the happy path.

#![allow(unused)]
fn main() {
pub struct Tokens<'a> { rest: &'a str }
}

The lifetime 'a ties every returned token to the original input buffer. If the input is stack-allocated or owned by the caller, no heap allocation is needed to parse a complete command.

  • Rust: The joy of safe zero-copy parsers -- ITNEXT

Error as data

ParseError is a typed enum. Each variant encodes exactly one failure mode with all the context needed to act on it:

#![allow(unused)]
fn main() {
pub enum ParseError {
    UnknownCommand(Box<str>),   // the bad token for diagnostics
    MissingArgument,
    InvalidResource,
    TrailingInput,
}
}

Box<str> in UnknownCommand avoids an allocation on every valid command parse: the allocation only occurs when parsing has already failed. The caller uses an exhaustive match to decide the response (send ko\n, log, close connection) without re-inspecting the raw string.

Error handling philosophy

The parser uses ? throughout. The first error terminates the parse and propagates to handle_command.rs, which sends ko\n to the client and leaves the pending-command queue unchanged.

unwrap() and expect() are banned in all non-test code. Every fallible operation propagates its error upward. This preserves information: the caller can distinguish a missing argument from an unknown command and respond appropriately.
