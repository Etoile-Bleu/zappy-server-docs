Zappy Server

Player

Source: server/src/world/player/

Player is the central entity of the Zappy domain. It has a unique identity (PlayerId), mutable state, and behavioral invariants that are enforced by its API rather than by caller discipline.

Structure

#![allow(unused)]
fn main() {
pub struct Player {
    pub id: PlayerId,
    pub x: u32,
    pub y: u32,
    pub direction: Direction,
    pub level: u8,
    pub inventory: Resources,
    pub actions: ActionQueue,
    pub frozen: bool,      // true during incantation
    food_ticks_remaining: u32,   // private
}
}

food_ticks_remaining is private. Only tick_food() may access it, which guarantees the invariant: for any living player, this counter is always in [1, 126].

Entity pattern

A domain entity has a unique identity and mutable state. PlayerId(u32) is the identity. Two players with the same coordinates but different ids are distinct entities; two players with the same id at different coordinates are the same entity in different states.

The entity pattern is contrasted with Value Objects (like Direction and Resources), which have no identity and are equal when all their fields are equal.

Reference: Evans Classification -- Martin Fowler

Direction: value object

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Direction { North, East, South, West }
}

Direction derives Copy and is passed by value. The rotation methods return a new Direction rather than mutating self:

#![allow(unused)]
fn main() {
player.direction = player.direction.turn_right();
}

Chaining is natural because each call returns the same type:

#![allow(unused)]
fn main() {
let facing_south = Direction::North.turn_right().turn_right();
}

to_delta() returns the (dx, dy) pair for one step forward. The coordinate convention (North = (0, -1), South = (0, +1)) is encoded in the tests.

Two-variable food model

Food management uses two separate variables:

  • inventory.food: food stones carried. Displayed by Inventory command and PlayerInventory GUI notification.
  • food_ticks_remaining: private countdown from 126 to 0. When it reaches 0, one stone is consumed.
stateDiagram-v2
    direction LR
    [*] --> Alive: food=10, ticks=126
    Alive --> Alive: tick_food() true (ticks 1..125)
    Alive --> StoneConsumed: tick 126 - ticks=0, food 10->9, reset to 126
    StoneConsumed --> Alive: continue
    Alive --> Dead: tick 1260 - ticks=0, food 1->0, returns false
    Dead --> [*]

The survival guarantee: a freshly spawned player with 10 food survives exactly 10 * 126 = 1260 ticks.

The alternative (a single counter food_units * 126) would produce 1386 ticks for 10 initial stones because the timer runs before the first stone is consumed. The two-variable model is correct by construction.

Command pattern: ActionQueue

#![allow(unused)]
fn main() {
pub struct ActionQueue { actions: VecDeque<Action> }
}

Action is a closed enum where each variant is a first-class value:

#![allow(unused)]
fn main() {
pub enum Action {
    Forward, TurnRight, TurnLeft, Look, Inventory,
    Broadcast(String), ConnectNbr, Fork, Eject,
    Take(ResourceKind), Set(ResourceKind), Incantation,
}
}

time_cost() returns the execution cost without any mutable state. This makes the queue a pure data structure. The execution logic lives in utils/actions/, not in the action itself.

#![allow(unused)]
fn main() {
let cost = action.time_cost();   // pure, no side effects
player.enqueue_action(action);   // queued, not executed
}

Queue as protocol contract

ActionQueue wraps a VecDeque<Action> with a hard capacity of 10. push returns false when the queue is full rather than panicking or silently dropping. The spec states:

"The client can send up to 10 requests in a row without any response. Over 10, the server will no longer take them into account."

The capacity is enforced by the type. Any code that calls push handles the false case explicitly.
