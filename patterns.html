Zappy Server

Design patterns reference

This chapter catalogs every design pattern used in the server, with definitions, rationale, and links to authoritative sources. Patterns are ordered by category.

Architectural patterns

Hexagonal architecture (ports and adapters)

What it is: The application core (domain) is surrounded by ports (interfaces) and adapters (implementations). The core never depends on infrastructure.

Where used: The entire server. world/ imports nothing from network/ or protocol/. The wire encoding for Direction::North (integer 1) lives exclusively in protocol/gui/format/player.rs.

Why: The domain can be tested, evolved, and reasoned about without any network or protocol setup. Tests for World, Player, and Map do not require a TCP socket.

Sources:

  • Hexagonal Architecture -- Alistair Cockburn (2005)
  • Ports and Adapters -- Herberto Graca (2017)

Functional core, imperative shell

What it is: Code is split into a pure inner core (no side effects) and an impure outer shell (I/O, mutation).

Where used: All three parsers and the GUI serializer are pure functions. app.rs, the reactor, and utils/actions/ are the imperative shell.

Why: The pure core is trivially testable. The shell is small and clearly bounded. Bugs in the network layer cannot corrupt parser behavior.

Sources:

  • Functional Core, Imperative Shell -- Gary Bernhardt (2012)
  • Patterns of Functional Programming -- Javier Casas

Concurrency and I/O patterns

Reactor pattern

What it is: A single thread demultiplexes I/O events using an OS poll facility and dispatches each event to a registered handler.

Where used: server/src/network/reactor.rs. One reactor manages all TCP connections and the game clock.

Why: Avoids one thread per client. Suitable for a game server with many idle GUI observers and a bounded number of AI players.

Sources:

  • Reactor: An Object Behavioral Pattern -- Douglas Schmidt (1995)
  • Reactor Pattern -- Wikipedia

Domain patterns (DDD)

Entity

What it is: An object defined by its unique identity rather than its attribute values. Two entities with the same attributes but different ids are distinct.

Where used: Player (identified by PlayerId). The player struct has mutable state; its identity is stable across all mutations.

Sources:

  • Evans Classification -- Martin Fowler
  • Domain-Driven Design -- Eric Evans (2003)

Value object

What it is: An object with no conceptual identity, defined entirely by its attribute values. Two value objects with the same attributes are interchangeable.

Where used:

  • Direction (North/East/South/West -- derives Copy, methods return new values)
  • Resources (seven counters -- derives Default, Clone, PartialEq)
  • Egg (position + team name -- immutable after creation, removed rather than mutated)

Sources:

  • Evans Classification -- Martin Fowler
  • Value Object -- refactoring.guru

Aggregate root

What it is: A cluster of domain objects accessed through a single entry point that enforces all invariants for the cluster.

Where used: World is the aggregate root. All game state (map, players, eggs, teams) is accessed through one World instance. The event loop holds one exclusive mutable reference to World.

Sources:

  • Aggregate -- Martin Fowler

Domain service (free function)

What it is: An operation that does not naturally belong to any single entity or value object, implemented as a free function.

Where used: take_resource(tile, player, kind) and drop_resource(tile, player, kind) operate on both a Tile and a Player. Placing this logic on either type would create an unwanted import dependency.

Sources:

  • Domain Service -- Domain-Driven Design Reference

Behavioral patterns

Command pattern

What it is: An operation is encapsulated as an object, enabling parameterization, queuing, and deferred execution.

Where used: Action enum. Each AI command is a first-class value stored in ActionQueue. time_cost() is a pure method on the value. Execution logic lives in utils/actions/, not in the action itself.

Sources:

  • Command Pattern -- Refactoring Guru
  • Command -- Gang of Four (1994)

Parsing patterns

Parse, don't validate

What it is: Instead of validating raw input and passing it alongside a trust assumption, parse it once into a type that makes invalid states unrepresentable.

Where used: Every parser in the server (protocol::ai::parse, protocol::gui::parse, cli::ServerArgs::from_args). The game engine never receives a raw string for a command or flag.

Sources:

  • Parse, don't validate -- Alexis King (2019)
  • Parse, Don't Validate -- DevIQ

LL(1) predictive parser

What it is: A top-down parser that reads one token of lookahead and immediately selects the correct production rule without backtracking.

Where used: protocol::ai::parse, protocol::gui::parse, cli::ServerArgs::from_args. The grammar of each protocol is flat and unambiguous; one lookahead token is always sufficient.

Sources:

  • Classification of Top Down Parsers -- GeeksforGeeks
  • LL(1) grammars -- UW Madison

Zero-copy cursor

What it is: A parser traverses input by advancing a reference or slice pointer, never allocating a copy of the underlying bytes.

Where used: Tokens<'a> in protocol::ai::lexer and protocol::gui::lexer. The lifetime 'a ties returned tokens to the original input buffer.

Sources:

  • Rust: The joy of safe zero-copy parsers -- ITNEXT
  • How to Create Zero-Copy Parsers in Rust -- OneUptime

Structural patterns

Newtype pattern

What it is: A single-field struct that wraps a primitive to create a distinct type with no runtime overhead.

Where used: PlayerId(u32), EggId(u32), Token(usize). The compiler rejects passing a tile coordinate where a player id is expected.

Sources:

  • New Type Idiom -- Rust By Example
  • Newtype -- Rust Design Patterns
  • Item 6: Embrace the newtype pattern -- Effective Rust

Information hiding (Parnas decomposition)

What it is: A module hides design decisions that are likely to change behind a stable interface. Only the interface is visible; internals are not.

Where used: format/player.rs and format/world.rs declare all helpers pub(super). No code outside format/mod.rs can call them. The wire encoding for orientation integers and resource indices is a hidden implementation detail.

Sources:

  • On the criteria to be used in decomposing systems into modules -- David Parnas (1972)
  • Visibility and privacy -- The Rust Reference

Memory and resource management

RAII (Resource Acquisition Is Initialization)

What it is: A resource (memory, file descriptor, socket) is tied to the lifetime of a Rust value. Dropping the value releases the resource.

Where used: Client owns its TcpStream. When the Client is removed from the reactor's HashMap, Rust calls Drop on the TcpStream, closing the file descriptor automatically. No explicit close is needed; no socket can leak.

Sources:

  • RAII -- Wikipedia
  • RAII -- Rust By Example

Flat buffer (contiguous 2D storage)

What it is: An N-dimensional array stored as a single contiguous block of memory, indexed by an arithmetic formula.

Where used: Map stores all tiles in a Vec<Tile> with the formula index = y * width + x. The alternative Vec<Vec<Tile>> has one extra indirection per row.

Sources:

  • Row- and column-major order -- Wikipedia

RNG

Linear congruential generator (LCG)

What it is: A pseudo-random number generator defined by the recurrence X_{n+1} = (a * X_n + c) mod m, where a, c, m are carefully chosen constants.

Where used: world::Rng uses the Knuth MMIX constants. Two generators with the same seed produce identical sequences, making map initialization reproducible.

Sources:

  • Linear congruential generator -- Wikipedia
  • Knuth, The Art of Computer Programming Vol. 2 -- Stanford
