Zappy Server

GUI Notifications

Source: server/src/protocol/gui/notification.rs, server/src/protocol/gui/format/

The serializer is the outbound half of the GUI protocol. Where the parser converts bytes into typed commands, the serializer converts typed notifications into wire strings.

The format Function

#![allow(unused)]
fn main() {
pub fn format(notification: &GuiNotification) -> String
}

A pure function: same input always produces the same output. No state, no I/O. The return type is String (never Result) because serializing well-typed data cannot fail.

#![allow(unused)]
fn main() {
let line = format(&GuiNotification::MapSize { width: 10, height: 20 });
assert_eq!(line, "msz 10 20\n");
}

Design patterns

Pure function

The format function has no observable side effects. This makes it the canonical example of a functional core component: given a typed notification, it always returns the same string. Testing requires no mocks, no setup, and no teardown.

If a wrong string reaches a GUI client, the entire call chain collapses to one function call and one input value. Debugging is trivially scoped.

Reference: Functional Core, Imperative Shell -- Gary Bernhardt (2012)

Exhaustive dispatch

Rust's match on GuiNotification must cover every variant. Adding a new notification type to the enum and forgetting to add the format arm is a compile error. The compiler acts as a completeness enforcer across the entire protocol.

Information hiding via pub(super)

Every helper function in format/player.rs and format/world.rs is declared pub(super): visible only to format/mod.rs. No external code can call player::player_death(...) directly. The wire format details (orientation integers, resource indices, # prefix) are internal decisions hidden behind the single public format() function.

If the protocol changes orientation encoding from 1-4 to compass letters, only format/player.rs::orientation_code changes. Every caller is untouched.

Reference: On the criteria to be used in decomposing systems into modules -- David Parnas (1972)

Stringly-Typed Avoidance

The game engine constructs a typed GuiNotification::PlayerPosition with a PlayerId, a u32 x/y pair, and an Orientation enum. It never builds a "ppo #1 3 4 2\n" string directly. The encoding from domain values to wire integers happens in one place and is never duplicated.

This is the output-side complement of Parse, Don't Validate: Format, Don't Encode.

Incremental string building (IncantationStart)

IncantationStart carries a variable-length list of participant player ids. Rather than collecting ids into an intermediate Vec<String> and joining, the helper appends each id directly to the output buffer with push_str:

#![allow(unused)]
fn main() {
let mut output = format!("pic {} {} {}", x, y, level);
for player in players {
    output.push(' ');
    output.push('#');
    output.push_str(&player.0.to_string());
}
output.push('\n');
}

One String allocation grows in place instead of creating and discarding multiple intermediate strings. This is the same approach as StringBuilder in Java or strings.Builder in Go.

Reference: Effective String Handling in Rust -- LogRocket Blog
