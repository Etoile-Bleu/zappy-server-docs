Zappy Server

Introduction

Zappy is a networked programming game where autonomous AI agents compete on a resource-rich 2D toroidal planet called Trantor. The server is the referee: it manages the simulation, enforces the wire protocol, and produces all observable game events.

This book documents the server only. The AI client, the graphical interface, and the build pipeline are covered separately.

What the server does

flowchart TD
    AI["AI Clients<br/>(Trantorian drones)"] -->|"TCP / AI protocol"| S["Server"]
    GUI["GUI Clients<br/>(observers)"] -->|"TCP / GUI protocol"| S
    S -->|"ppo, pnw, bct …"| GUI
    S -->|"ok / ko / dead"| AI
    S -->|"seg team"| AI
    S -->|"seg team"| GUI

The server has five responsibilities:

  1. Accept and classify connections. Each new TCP client is Unknown. Its first line identifies it: GRAPHIC promotes it to a GUI observer; a valid team name promotes it to an AI player and spawns a Trantorian drone from a team egg.

  2. Run the simulation clock. The frequency argument -f sets how many time units elapse per second. Every time unit drives food timers, action timers, and periodic resource respawn.

  3. Execute game actions. When an AI client's action timer expires, the server executes the action: moving a player, transferring a resource, launching an incantation, and so on.

  4. Broadcast GUI notifications. After every state change, the server serializes a typed GuiNotification and sends it to every connected GUI client.

  5. Enforce the win condition. When six players of the same team reach level 8, the server broadcasts seg team_name to all clients.

Hexagonal architecture

The server follows the Ports and Adapters pattern introduced by Alistair Cockburn in 2005. The central idea: the domain should be independent of the delivery mechanism. Whether the outside world communicates through TCP, a test harness, or a future RPC layer, the World struct and its invariants remain unchanged.

Ports are the boundary interfaces:

  • Inbound: NetworkEvent (raw bytes from clients), WorldEvent (timer expiry, starvation)
  • Outbound: GuiNotification (serialized and pushed to GUI clients)

Adapters translate between ports and the domain:

  • protocol::ai and protocol::gui parse raw bytes into typed commands
  • protocol::gui::format serializes typed notifications into wire strings
  • utils/actions/ maps typed commands to domain mutations

The critical rule: world/ imports nothing from protocol/ or network/. The wire encoding for Direction::North (integer 1) lives exclusively in protocol::gui::format::player::orientation_code. The domain type carries no protocol knowledge.

References:

  • Hexagonal Architecture -- Alistair Cockburn (2005)
  • Ports and Adapters -- Herberto Graca (2017)

Functional core, imperative shell

Gary Bernhardt's 2012 pattern structures code around two distinct zones:

  • Functional core: pure functions with no side effects. All parsers (protocol::ai::parse, protocol::gui::parse, protocol::gui::format) live here. Given an input, they return an output. No sockets, no state, no mutable globals.
  • Imperative shell: code that manages side effects. The reactor, app.rs, and utils/actions/ live here. They mutate world state, write to sockets, and schedule ticks.

This split makes the functional core trivially testable (no mocks, no setup, no teardown) and the imperative shell clearly bounded in scope.

The Reactor

The network layer is a single-threaded, non-blocking TCP event loop. It handles many concurrent clients without creating one thread per connection, frames newline-delimited commands, buffers response bytes, and drives the game clock.

Source: server/src/network/

The reactor pattern

The Reactor pattern was formally described by Douglas Schmidt in 1995. Its core insight: rather than giving each I/O source its own thread, register all sources with a single demultiplexer and let it call the right handler when a source is ready.

flowchart TD
    A["Register handlers<br/>(Listener + Clients)"] --> B
    B["poll(fds, timeout)"] --> C{Ready?}
    C -->|"readable/writable"| D["Handler::on_event()"]
    C -->|"timeout"| E["Run game ticks"]
    D --> F["Apply deferred<br/>register/remove/stop"]
    F --> B
    E --> B

The reactor never blocks waiting for one specific client. If client A is slow, clients B and C continue to be served. This is the fundamental advantage over a thread-per-client model for a game server with many idle spectators.

References:

  • Reactor: An Object Behavioral Pattern -- Douglas Schmidt (1995)
  • Reactor Pattern -- Wikipedia
  • Understanding the Reactor Pattern -- DZone

Why poll(2) and not epoll or kqueue?

libc::poll receives an array of pollfd structures and returns which descriptors are ready. It scans all descriptors linearly, so latency grows with the number of connected clients (O(n)). epoll (Linux) and kqueue (BSD/macOS) avoid this by maintaining a kernel-side ready list (O(1) per event).

For a Zappy server with tens to low hundreds of clients, the linear scan is immaterial. poll is POSIX-standard, has a simpler API, and requires no platform-specific abstraction layer. The choice is deliberate: simplicity over premature scalability.

References:

  • poll(2) -- Linux man pages
  • Comparing poll vs epoll -- Cloudflare Blog

Key types

Token

#![allow(unused)]
fn main() {
pub struct Token(pub usize);
}

A Token is the reactor's stable application-level identifier for a handler. File descriptors are not used as identities because the OS may reuse a file descriptor number after a socket is closed. Tokens increase monotonically and are never reused, making stale references safe to detect.

This is an instance of the Newtype pattern: a usize wearing a distinct type so the compiler rejects passing a player id or tile coordinate in its place.

Interest

#![allow(unused)]
fn main() {
pub enum Interest { Read, Write, ReadWrite }
}

A handler declares which readiness events it wants. A client with nothing to send registers Read only. When bytes are queued for writing, the reactor re-registers it as ReadWrite to also receive POLLOUT events. Returning to Read after the flush prevents a busy loop because TCP sockets are almost always writable.

Handler trait

#![allow(unused)]
fn main() {
pub trait Handler {
    fn fd(&self) -> RawFd;
    fn interest(&self) -> Interest;
    fn on_event(&mut self, event: Event, ctx: &mut ReactorContext) -> io::Result<()>;
    // optional capabilities with default no-op implementations:
    fn connected_event(&self, _token: Token) -> Option<NetworkEvent> { None }
    fn disconnected_event(&self, _token: Token) -> Option<NetworkEvent> { None }
    fn add_res_buf(&mut self, _data: &[u8]) -> bool { false }
    fn flush(&mut self) -> NetworkResult<()> { Ok(()) }
}
}

flush is called by Reactor::flush_and_close to drain the write buffer to the socket before the handler is deregistered. This ensures queued response bytes reach the client even when the connection is closed immediately after sending (e.g., when a team has no available slots). Client implements flush by calling write_res_socket() synchronously; other handlers use the default no-op.

The Handler trait decouples the reactor from TCP-specific logic. A TcpListener, a Client, or a future timer pipe all slot into the same collection. Handlers are stored as Box<dyn Handler>, a Rust trait object: different concrete types share one HashMap, with the correct on_event selected at runtime via a vtable.

References:

  • Trait Objects -- The Rust Programming Language

Deferred commands

While on_event holds a mutable borrow of a handler, the reactor cannot be mutated simultaneously (Rust's borrow checker enforces this). Adding or removing another handler inside on_event would require a second mutable borrow of the reactor, which the compiler rejects.

The solution: handlers append commands to a ReactorContext that the reactor processes after the current dispatch completes.

sequenceDiagram
    participant Reactor
    participant Handler
    participant Ctx as ReactorContext

    Reactor->>Handler: on_event(event, &mut ctx)
    Handler->>Ctx: ctx.register(new_handler)
    Handler->>Ctx: ctx.remove(old_token)
    Handler-->>Reactor: Ok(())
    Note over Reactor: dispatch complete
    Reactor->>Reactor: apply deferred commands
    Reactor->>Reactor: new handler registered
    Reactor->>Reactor: old handler removed

This pattern is a form of command queue: structural mutations are expressed as data, deferred until safe to apply. It is both a Rust borrowing solution and a design principle: handler dispatch is stable within an event-loop iteration.

Line framing

TCP is a byte stream. One read call may deliver half a command, one command, or multiple commands concatenated. Each Client accumulates bytes in a request: Vec<u8> buffer and calls next_command after each read to extract complete lines:

read #1: b"forw"
buffer:  b"forw"              -> no complete line

read #2: b"ard\nleft\ninv"
buffer:  b"forward\nleft\ninv"
  -> emit "forward"
  -> emit "left"
remaining: b"inv"

Both Unix (\n) and DOS (\r\n) line endings are accepted. Command bytes are forwarded to app.rs as raw Vec<u8> without UTF-8 conversion; the protocol parsers decide independently whether valid text is required.

The request buffer is capped at 4096 bytes. Exceeding this limit before the buffer drains disconnects the client, bounding memory use for misbehaving or hostile connections.

RAII and socket cleanup

Rust's ownership model provides RAII (Resource Acquisition Is Initialization) for free. A Client owns its TcpStream. When the Client is removed from the reactor's HashMap, the Drop implementation closes the file descriptor automatically. No explicit close call is required, and no socket can leak.

References:

  • RAII -- Wikipedia
  • RAII -- Rust By Example

Game tick scheduling

The reactor uses poll's timeout parameter to implement game ticks without a second thread. After each event-loop iteration, it computes the time remaining until the next tick and passes it as the poll timeout:

poll(fds, timeout_ms = millis_until_next_tick)
  • If a network event arrives first, poll returns early. The reactor processes the event, then loops back with a shorter timeout.
  • If the tick deadline arrives first, poll times out. The reactor calls the game tick callback, advances the World, and loops back.

If the server falls behind, it executes missed ticks in a catch-up loop capped at 50 per iteration. This prevents a severely late server from starving network I/O.

flowchart LR
    A["Compute timeout<br/>= next_tick - now"] --> B["poll(fds, timeout)"]
    B -->|"I/O ready"| C["Dispatch handlers"]
    B -->|"Timeout"| D["Run game ticks<br/>(capped at 50)"]
    C --> A
    D --> A

The protocol layer translates between raw TCP bytes and typed Rust values. It has two halves that are deliberately symmetric and independent:

All three functions are pure functions: given an input, they return an output, mutate nothing, and cause no side effects. This makes them trivially testable and impossible to misuse.

Shared design principles

Parse, Don't Validate

Coined by Alexis King in 2019, this principle states: instead of passing raw input alongside a trust assumption, parse it once into a type that makes invalid states unrepresentable.

Applied throughout this layer: neither app.rs nor any action handler ever sees a raw &str. Every value that crosses the parse boundary is either a typed AiCommand / GuiCommand, or a typed error. The caller cannot accidentally treat a tile Y-coordinate as a player id.

Reference: Parse, don't validate -- Alexis King (2019)

Newtype pattern

PlayerId(u32) and EggId(u32) are newtypes: single-field structs that give a u32 a distinct type identity. The compiler rejects passing one where the other is expected, at zero runtime cost.

References:

  • New Type Idiom -- Rust By Example
  • Newtype -- Rust Design Patterns
  • Item 6: Embrace the newtype pattern -- Effective Rust

Exhaustive pattern matching

Rust's match on an enum must cover every variant. Adding a new GuiNotification variant without updating format() is a compile error, not a runtime surprise. This compiler-enforced completeness eliminates an entire category of protocol bugs.

Reference: Pattern and exhaustiveness checking -- Rust Compiler Development Guide

Connection handshake

Before a client is classified as Ai, it is Unknown. The first line it sends determines its type:

stateDiagram-v2
    [*] --> Unknown: TCP connected, WELCOME\n sent
    Unknown --> Gui: first line == "GRAPHIC"
    Unknown --> Ai: first line == valid team name with available slot
    Unknown --> [*]: team unknown / no slot / no egg
    Ai --> Ai: subsequent commands queued
    Gui --> Gui: GUI queries handled

On successful AI promotion, the server:

  1. Picks a random egg from the team.
  2. Spawns a Player at the egg's position.
  3. Registers the Token -> PlayerId mapping in State.
  4. Replies with remaining_slots\n then width height\n.
  5. Broadcasts pnw #id X Y O L team\n to all GUI clients.
  6. Broadcasts ebo #egg_id\n to all GUI clients (egg hatched).

Full team: When spawn_player_from_team_egg returns NoSlotsAvailable, the server sends 0\n then W H\n (zero slots + dimensions), flushes synchronously via flush_and_close, and disconnects the client.

Unknown team: The server sends ko\n and closes the connection immediately without sending slot count or dimensions.

Design patterns

LL(1) predictive parser

The parser is an LL(1) (Left-to-right, Leftmost derivation, 1-token lookahead) predictive parser. It reads one token (the command name) and immediately knows which branch to take. The Zappy AI grammar has no ambiguity and no recursion, so a flat match on the command name is sufficient.

flowchart TD
    INPUT["'Take food'"] --> LEXER["Tokens::next_str()"]
    LEXER --> CMD{"command name?"}
    CMD -->|"Forward"| FWD["Ok(AiCommand::Forward)"]
    CMD -->|"Take"| RES["Tokens::next_str() = food"]
    RES --> KIND{"ResourceKind?"}
    KIND -->|"food"| TAKE["Ok(AiCommand::Take(Food))"]
    KIND -->|"diamond"| ERR["Err(InvalidResource)"]
    CMD -->|"unknown"| UNK["Err(UnknownCommand)"]

References:

  • Classification of Top Down Parsers -- GeeksforGeeks
  • LL(1) grammars -- UW Madison lecture notes

Zero-copy cursor

The Tokens<'a> struct holds a &'a str slice that shrinks as tokens are consumed. Returned tokens are also &'a str slices borrowing from the original input. No String allocation occurs on the happy path.

#![allow(unused)]
fn main() {
pub struct Tokens<'a> { rest: &'a str }
}

The lifetime 'a ties every returned token to the original input buffer. If the input is stack-allocated or owned by the caller, no heap allocation is needed to parse a complete command.

References:

  • Rust: The joy of safe zero-copy parsers -- ITNEXT
  • How to Create Zero-Copy Parsers in Rust -- OneUptime Blog

Error as data

ParseError is a typed enum. Each variant encodes exactly one failure mode with all the context needed to act on it:

#![allow(unused)]
fn main() {
pub enum ParseError {
    UnknownCommand(Box<str>),   // the bad token for diagnostics
    MissingArgument,
    InvalidResource,
    TrailingInput,
}
}

Box<str> in UnknownCommand avoids an allocation on every valid command parse: the allocation only occurs when parsing has already failed. The caller uses an exhaustive match to decide the response (send ko\n, log, close connection) without re-inspecting the raw string.

Error handling philosophy

The parser uses ? throughout. The first error terminates the parse and propagates to handle_command.rs, which sends ko\n to the client and leaves the pending-command queue unchanged.

unwrap() and expect() are banned in all non-test code. Every fallible operation propagates its error upward. This preserves information: the caller can distinguish a missing argument from an unknown command and respond appropriately.

Parsing a player ID

Player IDs on the wire are prefixed with #: ppo #3 means player 3. Tokens::next_player_id strips the # prefix with strip_prefix, then parses the remaining digits into a u32 wrapped in PlayerId. The # prefix is the wire format concern; the domain type PlayerId(u32) carries no #.

    STRIP --> PARSE["parse u32 = 3"]

Separation of lexing and parsing

Two stages are kept deliberately separate:

  • Lexing (lexer.rs): converts &str into a stream of typed tokens via a zero-copy cursor. No heap allocation on the happy path.
  • Parsing (parse.rs): converts the token stream into a GuiCommand. The command name is the sole lookahead token.

Adding a new command requires only two changes: a new variant in GuiCommand and a new match arm in parse(). The lexer never changes for new commands.

Design patterns

Pure function

The format function has no observable side effects. This makes it the canonical example of a functional core component: given a typed notification, it always returns the same string. Testing requires no mocks, no setup, and no teardown.

If a wrong string reaches a GUI client, the entire call chain collapses to one function call and one input value. Debugging is trivially scoped.

Reference: Functional Core, Imperative Shell -- Gary Bernhardt (2012)

Exhaustive dispatch

Rust's match on GuiNotification must cover every variant. Adding a new notification type to the enum and forgetting to add the format arm is a compile error. The compiler acts as a completeness enforcer across the entire protocol.

Information hiding via pub(super)

Every helper function in format/player.rs and format/world.rs is declared pub(super): visible only to format/mod.rs. No external code can call player::player_death(...) directly. The wire format details (orientation integers, resource indices, # prefix) are internal decisions hidden behind the single public format() function.

If the protocol changes orientation encoding from 1-4 to compass letters, only format/player.rs::orientation_code changes. Every caller is untouched.

Reference: On the criteria to be used in decomposing systems into modules -- David Parnas (1972)

Stringly-Typed Avoidance

The game engine constructs a typed GuiNotification::PlayerPosition with a PlayerId, a u32 x/y pair, and an Orientation enum. It never builds a "ppo #1 3 4 2\n" string directly. The encoding from domain values to wire integers happens in one place and is never duplicated.

This is the output-side complement of Parse, Don't Validate: Format, Don't Encode.

Incremental string building (IncantationStart)

Design patterns

Single mutable owner

All game state lives in World. There is no shared ownership (Arc, Mutex), no channels, no background threads. The event loop holds one World value and mutates it by calling advance_tick once per time unit.

This approach eliminates an entire class of concurrency bugs. A Rust &mut World is an exclusive mutable reference; the borrow checker guarantees no other code can read or write world state while advance_tick runs.

Action timer colocation

Each Player holds its own action_ticks_remaining: u32. The alternative (a HashMap<PlayerId, u32> on World) would require two structures to stay in sync whenever a player is removed.

Keeping the timer on the player makes removal trivial: removing the player from world.players deletes the timer automatically.

Respawn determinism

#![allow(unused)]
fn main() {
if self.tick % RESPAWN_PERIOD == 0 { ... }   // fires at 20, 40, 60, ...
}

Respawn fires at absolute multiples of 20, not 20 ticks after the last fire. If the server catches up after a stall, multiple missed respawns execute sequentially but at the correct tick numbers. Behavior is deterministic and independent of wall-clock time.

Initial slot model

World::new calls Team::new(name, 0) and then team.add_egg(id) once per client slot. This ensures available_slots always equals the number of eggs on the map. Every connection goes through the remove_egg path, which handles both slot accounting and egg position lookup in one operation.

Toroidal Map

Source: server/src/world/map.rs

Map is a 2D toroidal grid of tiles. Every coordinate access wraps automatically; there are no bounds checks that can fail at runtime.

Flat buffer layout

The map is stored as a single contiguous Vec<Tile> in row-major order:

index = y * width + x

The alternative, Vec<Vec<Tile>>, requires one heap allocation per row and one pointer dereference per row access. The flat layout has a single allocation and exploits spatial locality: tiles on the same row are adjacent in memory, making sequential access cache-friendly.

Single point of truth for indexing

All coordinate-to-index arithmetic lives in one private method:

#![allow(unused)]
fn main() {
fn flat_index(&self, x: u32, y: u32) -> usize {
    (y as usize) * (self.width as usize) + (x as usize)
}
}

get, get_mut, Index, and IndexMut all delegate to flat_index. If the formula ever needs to change, there is exactly one place to edit and one place to test.

Reference: Single source of truth -- Wikipedia

Toroidal arithmetic

Movement uses signed deltas applied to unsigned coordinates. Naive subtraction underflows; a single % returns negative values in Rust. The solution uses i64 intermediates and rem_euclid:

#![allow(unused)]
fn main() {
pub fn offset(&self, x: u32, y: u32, dx: i32, dy: i32) -> (u32, u32) {
    let nx = ((x as i64 + dx as i64).rem_euclid(self.width as i64)) as u32;
    let ny = ((y as i64 + dy as i64).rem_euclid(self.height as i64)) as u32;
    (nx, ny)
}
}

rem_euclid always returns a non-negative value, so wrapping past the left or top edge works correctly:

(-1).rem_euclid(10) == 9   // wraps to the right edge
(-1) % 10           == -1  // wrong for toroidal semantics

Player is the central entity of the Zappy domain. It has a unique identity (PlayerId), mutable state, and behavioral invariants that are enforced by its API rather than by caller discipline.

Entity pattern

A domain entity has a unique identity and mutable state. PlayerId(u32) is the identity. Two players with the same coordinates but different ids are distinct entities; two players with the same id at different coordinates are the same entity in different states.

The entity pattern is contrasted with Value Objects (like Direction and Resources), which have no identity and are equal when all their fields are equal.

Forward computes the new position using Direction::to_delta and Map::offset (toroidal wrapping), updates the tile player lists, updates the player struct, and broadcasts ppo to all GUI clients.

Look

Look constructs the visible tile list based on the player's level and orientation. At level L, the player sees (L+1)^2 tiles arranged in a frontward-expanding diamond: the current tile, then L rows ahead each wider by 2 tiles.

Level 1: [self] [front-left, front, front-right]  (4 tiles)
Level 2: [self] [3 tiles at row 1] [5 tiles at row 2]  (9 tiles)

Each tile is formatted as a space-separated list of contents: player, food, linemate, etc.

Broadcast

Broadcast computes the direction K (1-8) from each receiver's perspective using shortest-path toroidal geometry. K=0 means the sender and receiver share the same tile. The receiver gets message K, text\n; the sender gets ok\n. The pbc notification goes to all GUI clients.

Eject

Eject pushes all players and destroys all eggs on the caster's tile in the caster's facing direction. Pushed players move to the adjacent tile in that direction (toroidal). Each pushed player receives eject: K\n where K is the push direction. GUI clients receive pex for each pushed player and edi for each destroyed egg.

Fork

Fork allocates a new EggId, creates an Egg at the player's current position, registers it with the team (incrementing available_slots), and sends pfk + enw to all GUI clients. The egg persists until a new AI client hatches from it or an Eject destroys it.

Resource commands

Take moves one unit of the named resource from the tile to the player inventory, sends ok\n or ko\n, and on success broadcasts pgt and the updated bct to all GUI clients. Set does the inverse.

Both use take_resource and drop_resource free functions (domain service pattern) to operate on both the Tile and the Player atomically.

Incantation

Source: server/src/utils/actions/incantation/, server/src/utils/commands/handle_ai_command.rs

Incantation is the elevation ritual. A group of players of the same level on the same tile can collectively raise their level by consuming specific stones. The ritual takes 300 time units (300/f seconds).

Two-phase design

Incantation uses a two-phase commit: preconditions are verified immediately at queue time (Phase 1), and the ritual executes after the 300-tick countdown (Phase 2). This prevents a player from queuing an incantation that had no chance of succeeding.

Participant collection

#![allow(unused)]
fn main() {
pub(crate) fn collect_participants(
    world: &World,
    x: u32,
    y: u32,
    level: u8,
) -> Vec<PlayerId> {
    world.map.get(x, y).players.iter()
        .filter(|&&pid| {
            world.players.get(&pid)
                .is_some_and(|p| p.level == level && !p.frozen)
        })
        .copied()
        .collect()
}
}

Only players on the same tile, at the same level as the initiator, and not already frozen in another incantation qualify. The initiating player is always included (they are on the tile and not yet frozen at collection time).

ActiveIncantation

Between Phase 1 and Phase 2 the world stores which participants were locked in:

#![allow(unused)]
fn main() {
pub struct ActiveIncantation {
    pub initiator: PlayerId,
    pub participants: Vec<PlayerId>,
}
}

World.active_incantations: Vec<ActiveIncantation> holds one entry per in-flight ritual. At Phase 2 fire time, incantation/mod.rs removes the matching entry by initiator and re-verifies each participant's position, level, and frozen state against the tile's current resources.

Resource consumption

tile.resources.consume(&req.resources) subtracts all required stones in one call after has_enough confirms they are present. This is an atomic operation: if has_enough returns true, consume will not panic.

Freeze flag

player.frozen is set to true at Phase 1 (queue time), immediately after conditions are confirmed and pic is broadcast. This prevents participants from executing new actions while the ritual is counting down.

A frozen player can still receive commands — they are buffered in the action queue — but tick_action will not fire any action while frozen == true. On ritual completion (success or failure), all participants are unfrozen and their queued actions resume normally.

Win condition

Source: server/src/utils/actions/incantation/victory.rs

After every successful incantation, check_victory scans all players for the win condition.

Condition

The game ends when six or more players of the same team simultaneously hold level 8 (MAX_LEVEL).

#![allow(unused)]
fn main() {
const WIN_THRESHOLD: u32 = 6;
}

Algorithm

flowchart TD
    A["check_victory(ctx)"] --> B["find_winning_team(ctx)"]
    B --> C["Build HashMap per team<br/>count players at level 8"]
    C --> D{any count >= WIN_THRESHOLD?}
    D -->|yes| E["broadcast 'seg team'<br/>to all GUI clients"]
    D -->|no| F["return Ok(())"]
    E --> G["return Ok(())"]

find_winning_team uses State::token_for(player_id) and State::client_type(token) to recover the team name from a Player. The Player struct itself stores no team field; team membership is tracked through the State client map.

Broadcast and shutdown

#![allow(unused)]
fn main() {
GuiNotification::GameEnd { team: winning_team }
// wire: "seg team_name\n"
}

seg is broadcast to all connected GUI clients via broadcast_gui. AI clients do not receive seg directly; their sockets are closed when the reactor stops.

After broadcasting, check_victory calls ctx.reactor.stop(), which sets the reactor's internal running flag to false. The event loop exits cleanly after the current iteration, closing all registered handlers.

Why check after every incantation?

The only way for a player to reach level 8 is through a successful incantation at level 7. Checking the win condition after every successful incantation guarantees the check fires at the earliest possible moment, with no polling overhead on ticks where no elevation occurred.

Design patterns

Parse, don't validate

The game engine never touches a raw argument string. It receives a ServerArgs with typed fields. The single parse boundary is ServerArgs::from_args(). Everything that crosses it is either a fully typed struct or a typed ArgsError.

Reference: Parse, don't validate -- Alexis King (2019)

Predictive token scan (LL(1))

Arguments are consumed left-to-right with an index cursor. Each token is examined once: if it starts with -, it is a flag; otherwise it is a value for the current flag. No backtracking. This is the same LL(1) pattern used in the GUI command parser, applied to a flat key-value list.

Generic helper: next_parsed<T>

A single generic function replaces what would otherwise be two identical functions next_u16 and next_u32:

#![allow(unused)]
fn main() {
fn next_parsed<T: FromStr>(flag: &str, args: &[String], idx: &mut usize)
    -> Result<T, ArgsError>
}

The type parameter is inferred from context. The constraint T: FromStr is the minimal and correct bound: the function only needs to call str::parse::<T>().

Reference: std::str::FromStr -- Rust Standard Library

Behavior belongs to its type

from_args is a constructor method on ServerArgs, not a free function:

#![allow(unused)]
fn main() {
let config = ServerArgs::from_args(&raw_args)?;
}

The call site reads as intent. A free function parse_args(&raw_args) says nothing about what it produces. The method form is self-documenting.

The -n flag

-n is the only variable-length flag. It collects all consecutive tokens that do not start with - as team names. Collection stops at the next flag or at end of input:

# Two team names collected, then -c recognized as the next flag
zappy_server -n red blue -c 2 -p 4242 -x 10 -y 10 -f 100

Team names must not start with -. This matches the spec which treats team names as plain identifiers.

Design patterns reference

This chapter catalogs every design pattern used in the server, with definitions, rationale, and links to authoritative sources. Patterns are ordered by category.

Architectural patterns

Hexagonal architecture (ports and adapters)

What it is: The application core (domain) is surrounded by ports (interfaces) and adapters (implementations). The core never depends on infrastructure.

Where used: The entire server. world/ imports nothing from network/ or protocol/. The wire encoding for Direction::North (integer 1) lives exclusively in protocol/gui/format/player.rs.

Why: The domain can be tested, evolved, and reasoned about without any network or protocol setup. Tests for World, Player, and Map do not require a TCP socket.

Sources:

  • Hexagonal Architecture -- Alistair Cockburn (2005)
  • Ports and Adapters -- Herberto Graca (2017)

Functional core, imperative shell

What it is: Code is split into a pure inner core (no side effects) and an impure outer shell (I/O, mutation).

Where used: All three parsers and the GUI serializer are pure functions. app.rs, the reactor, and utils/actions/ are the imperative shell.

Why: The pure core is trivially testable. The shell is small and clearly bounded. Bugs in the network layer cannot corrupt parser behavior.

Sources:

  • Functional Core, Imperative Shell -- Gary Bernhardt (2012)
  • Patterns of Functional Programming -- Javier Casas

Concurrency and I/O patterns

Reactor pattern

What it is: A single thread demultiplexes I/O events using an OS poll facility and dispatches each event to a registered handler.

Where used: server/src/network/reactor.rs. One reactor manages all TCP connections and the game clock.

Why: Avoids one thread per client. Suitable for a game server with many idle GUI observers and a bounded number of AI players.

Sources:

  • Reactor: An Object Behavioral Pattern -- Douglas Schmidt (1995)
  • Reactor Pattern -- Wikipedia

Domain patterns (DDD)

Entity

What it is: An object defined by its unique identity rather than its attribute values. Two entities with the same attributes but different ids are distinct.

Where used: Player (identified by PlayerId). The player struct has mutable state; its identity is stable across all mutations.

Sources:

  • Evans Classification -- Martin Fowler
  • Domain-Driven Design -- Eric Evans (2003)

Value object

What it is: An object with no conceptual identity, defined entirely by its attribute values. Two value objects with the same attributes are interchangeable.

Where used:

  • Direction (North/East/South/West -- derives Copy, methods return new values)
  • Resources (seven counters -- derives Default, Clone, PartialEq)
  • Egg (position + team name -- immutable after creation, removed rather than mutated)

Sources:

  • Evans Classification -- Martin Fowler
  • Value Object -- refactoring.guru

Aggregate root

What it is: A cluster of domain objects accessed through a single entry point that enforces all invariants for the cluster.

Where used: World is the aggregate root. All game state (map, players, eggs, teams) is accessed through one World instance. The event loop holds one exclusive mutable reference to World.

Sources:

  • Aggregate -- Martin Fowler

Domain service (free function)

What it is: An operation that does not naturally belong to any single entity or value object, implemented as a free function.

Where used: take_resource(tile, player, kind) and drop_resource(tile, player, kind) operate on both a Tile and a Player. Placing this logic on either type would create an unwanted import dependency.

Sources:

  • Domain Service -- Domain-Driven Design Reference

Behavioral patterns

Command pattern

What it is: An operation is encapsulated as an object, enabling parameterization, queuing, and deferred execution.

Where used: Action enum. Each AI command is a first-class value stored in ActionQueue. time_cost() is a pure method on the value. Execution logic lives in utils/actions/, not in the action itself.

Sources:

  • Command Pattern -- Refactoring Guru
  • Command -- Gang of Four (1994)

Parsing patterns

Parse, don't validate

What it is: Instead of validating raw input and passing it alongside a trust assumption, parse it once into a type that makes invalid states unrepresentable.

Where used: Every parser in the server (protocol::ai::parse, protocol::gui::parse, cli::ServerArgs::from_args). The game engine never receives a raw string for a command or flag.

Sources:

  • Parse, don't validate -- Alexis King (2019)
  • Parse, Don't Validate -- DevIQ

LL(1) predictive parser

What it is: A top-down parser that reads one token of lookahead and immediately selects the correct production rule without backtracking.

Where used: protocol::ai::parse, protocol::gui::parse, cli::ServerArgs::from_args. The grammar of each protocol is flat and unambiguous; one lookahead token is always sufficient.

Sources:

  • Classification of Top Down Parsers -- GeeksforGeeks
  • LL(1) grammars -- UW Madison

Zero-copy cursor

What it is: A parser traverses input by advancing a reference or slice pointer, never allocating a copy of the underlying bytes.

Where used: Tokens<'a> in protocol::ai::lexer and protocol::gui::lexer. The lifetime 'a ties returned tokens to the original input buffer.

Sources:

  • Rust: The joy of safe zero-copy parsers -- ITNEXT
  • How to Create Zero-Copy Parsers in Rust -- OneUptime

Structural patterns

Newtype pattern

What it is: A single-field struct that wraps a primitive to create a distinct type with no runtime overhead.

Where used: PlayerId(u32), EggId(u32), Token(usize). The compiler rejects passing a tile coordinate where a player id is expected.

Sources:

  • New Type Idiom -- Rust By Example
  • Newtype -- Rust Design Patterns
  • Item 6: Embrace the newtype pattern -- Effective Rust

Information hiding (Parnas decomposition)

What it is: A module hides design decisions that are likely to change behind a stable interface. Only the interface is visible; internals are not.

Where used: format/player.rs and format/world.rs declare all helpers pub(super). No code outside format/mod.rs can call them. The wire encoding for orientation integers and resource indices is a hidden implementation detail.

Sources:

  • On the criteria to be used in decomposing systems into modules -- David Parnas (1972)
  • Visibility and privacy -- The Rust Reference

Memory and resource management

RAII (Resource Acquisition Is Initialization)

What it is: A resource (memory, file descriptor, socket) is tied to the lifetime of a Rust value. Dropping the value releases the resource.

Where used: Client owns its TcpStream. When the Client is removed from the reactor's HashMap, Rust calls Drop on the TcpStream, closing the file descriptor automatically. No explicit close is needed; no socket can leak.

Sources:

  • RAII -- Wikipedia
  • RAII -- Rust By Example

Flat buffer (contiguous 2D storage)

What it is: An N-dimensional array stored as a single contiguous block of memory, indexed by an arithmetic formula.

Where used: Map stores all tiles in a Vec<Tile> with the formula index = y * width + x. The alternative Vec<Vec<Tile>> has one extra indirection per row.

Sources:

  • Row- and column-major order -- Wikipedia

RNG

Linear congruential generator (LCG)

What it is: A pseudo-random number generator defined by the recurrence X_{n+1} = (a * X_n + c) mod m, where a, c, m are carefully chosen constants.

Where used: world::Rng uses the Knuth MMIX constants. Two generators with the same seed produce identical sequences, making map initialization reproducible.

Sources:

  • Knuth, The Art of Computer Programming Vol. 2 -- Stanford
