Zappy Serveur

Monde et système de temps

Source : server/src/world/world.rs

World est la racine d'agrégat de la couche domaine. Il possède tout l'état mutable de jeu et expose une méthode de tick unique qui pilote l'ensemble de la simulation.

Structure

#![allow(unused)]
fn main() {
pub struct World {
    pub map: Map,
    pub teams: Vec<Team>,
    pub players: HashMap<PlayerId, Player>,
    pub eggs: HashMap<EggId, Egg>,
    pub active_incantations: Vec<ActiveIncantation>,
    pub tick: u64,
    pub freq: u32,
    // privés : spawner, next_player_id, next_egg_id
}

pub struct ActiveIncantation {
    pub initiator: PlayerId,
    pub participants: Vec<PlayerId>,
}
}

active_incantations suit les rituels d'incantation en cours entre la Phase 1 (moment de la mise en file) et la Phase 2 (moment de l'exécution). Voir Incantation pour la conception complète en deux phases.

players et eggs utilisent HashMap pour une recherche en O(1) par identifiant. teams utilise Vec car la recherche d'équipe se fait toujours par scan de nom sur une petite tranche (typiquement 2-8 équipes).

La boucle de ticks

sequenceDiagram
    participant App as app.rs
    participant World
    participant Player
    participant Spawner as ResourceSpawner

    App->>+World: advance_tick()
    World->>World: tick += 1
    loop pour chaque joueur
        World->>Player: tick_food()
        alt nourriture épuisée
            World->>World: supprimer joueur de la carte + players
            World-->>App: WorldEvent::PlayerStarved
        end
    end
    loop pour chaque joueur survivant
        World->>Player: tick_action()
        alt minuterie à zéro
            World-->>App: WorldEvent::ActionReady { action }
        end
    end
    alt tick % 20 == 0
        World->>Spawner: respawn(&mut map)
        World-->>App: WorldEvent::TilesUpdated { positions }
    end
    World-->>-App: Vec<WorldEvent>

WorldEvent

#![allow(unused)]
fn main() {
pub enum WorldEvent {
    PlayerStarved { player_id: PlayerId },
    ActionReady { player_id: PlayerId, action: Action },
    TilesUpdated { positions: Vec<(u32, u32)> },
}
}

advance_tick retourne les événements sous forme de données simples. Le World n'a aucune connaissance du réseau. C'est l'appelant (app.rs) qui envoie dead\n à un client IA affamé, diffuse pdi aux clients GUI, et exécute la logique de jeu pour une action déclenchée.

Cette conception suit le principe d'architecture pilotée par les événements au niveau du domaine : le monde annonce ce qui s'est passé ; la couche applicative décide quoi en faire.

Référence : Event-driven architecture - Martin Fowler

Patrons de conception

Propriétaire mutable unique

Tout l'état de jeu réside dans World. Pas de propriété partagée (Arc, Mutex), pas de canaux, pas de threads en arrière-plan. La boucle d'événements détient une valeur World et la mute en appelant advance_tick une fois par unité de temps.

Cette approche élimine toute une classe de bugs de concurrence. Un &mut World en Rust est une référence mutable exclusive ; le vérificateur d'emprunts garantit qu'aucun autre code ne peut lire ou écrire l'état du monde pendant qu'advance_tick s'exécute.

Colocalisation du minuteur d'action

Chaque Player détient son propre action_ticks_remaining: u32. L'alternative (un HashMap<PlayerId, u32> dans World) nécessiterait que deux structures restent synchronisées à chaque suppression d'un joueur.

Garder le minuteur sur le joueur rend la suppression triviale : supprimer le joueur de world.players efface automatiquement le minuteur.

Déterminisme du respawn

#![allow(unused)]
fn main() {
if self.tick % RESPAWN_PERIOD == 0 { ... }   // déclenche à 20, 40, 60, ...
}

Le respawn se déclenche aux multiples absolus de 20, pas 20 ticks après le dernier déclenchement. Si le serveur rattrape un retard, plusieurs respawns manqués s'exécutent séquentiellement mais aux numéros de tick corrects. Le comportement est déterministe et indépendant de l'heure murale.

Modèle de créneaux initiaux

World::new appelle Team::new(name, 0) puis team.add_egg(id) une fois par créneau client. Cela garantit que available_slots est toujours égal au nombre d'œufs sur la carte. Chaque connexion passe par le chemin remove_egg, qui gère à la fois la comptabilité des créneaux et la recherche de position de l'œuf en une seule opération.

SpawnedPlayer

spawn_player_from_team_egg retourne un SpawnedPlayer en cas de succès :

#![allow(unused)]
fn main() {
pub struct SpawnedPlayer {
    pub player_id: PlayerId,
    pub egg_id: EggId,
    pub x: u32,
    pub y: u32,
    pub remaining_slots: u32,
}
}

egg_id est l'identifiant de l'œuf qui a été consommé. La couche de handshake l'utilise pour diffuser ebo #egg_id aux clients GUI immédiatement après pnw.

Système de temps

Le serveur opère en unités de temps. Une unité de temps = 1 / freq secondes. Le réacteur appelle advance_tick une fois par unité de temps.

Exigence de la spécificationImplémentation
Compteur de tick global au taux f/sworld.tick incrémenté dans advance_tick
Temps d'exécution d'une action = coût / fenqueue_action fixe ticks = action.time_cost()
Minuteur d'action par joueurplayer.action_ticks_remaining décrémenté dans tick_action
Décrémentation de nourriture : 1 unité par 126 unités de tempstick_food décrémente food_ticks_remaining
Respawn des ressources toutes les 20 unités de tempstick % RESPAWN_PERIOD == 0

Règle : ne jamais utiliser les secondes de l'horloge murale dans la couche domaine. Si un appelant a besoin de secondes, il divise par freq à la frontière.
