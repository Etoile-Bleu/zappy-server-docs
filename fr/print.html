Zappy Serveur

Introduction

Zappy est un jeu de programmation en réseau où des agents IA autonomes s'affrontent sur une planète 2D toroïdale riche en ressources appelée Trantor. Le serveur est l'arbitre : il gère la simulation, applique le protocole réseau et produit tous les événements observables de la partie.

Ce livre documente uniquement le serveur. Le client IA, l'interface graphique et le pipeline de compilation sont couverts séparément.

Ce que fait le serveur

flowchart TD
    AI["Clients IA<br/>(drones trantorisés)"] -->|"TCP / protocole IA"| S["Serveur"]
    GUI["Clients GUI<br/>(observateurs)"] -->|"TCP / protocole GUI"| S
    S -->|"ppo, pnw, bct …"| GUI
    S -->|"ok / ko / dead"| AI
    S -->|"seg team"| AI
    S -->|"seg team"| GUI

Le serveur remplit cinq responsabilités :

  1. Accepter et classifier les connexions. Chaque nouveau client TCP est Unknown. Sa première ligne l'identifie : GRAPHIC le promut en observateur GUI ; un nom d'équipe valide le promut en joueur IA et fait éclore un drone trantorisé depuis un œuf de l'équipe.

  2. Piloter l'horloge de simulation. L'argument de fréquence -f détermine combien d'unités de temps s'écoulent par seconde. Chaque unité de temps déclenche les minuteries de nourriture, les minuteries d'action et la régénération périodique des ressources.

  3. Exécuter les actions de jeu. Lorsque la minuterie d'action d'un client IA expire, le serveur exécute l'action : déplacer un joueur, transférer une ressource, lancer une incantation, etc.

  4. Diffuser les notifications GUI. Après chaque changement d'état, le serveur sérialise une GuiNotification typée et l'envoie à tous les clients GUI connectés.

  5. Appliquer la condition de victoire. Lorsque six joueurs de la même équipe atteignent le niveau 8, le serveur diffuse seg nom_equipe à tous les clients.

Architecture hexagonale

Le serveur suit le patron Ports et Adaptateurs introduit par Alistair Cockburn en 2005. L'idée centrale : le domaine doit être indépendant du mécanisme de livraison. Que le monde extérieur communique via TCP, un harnais de test ou une future couche RPC, la structure World et ses invariants restent inchangés.

Les ports sont les interfaces de frontière :

  • Entrant : NetworkEvent (octets bruts des clients), WorldEvent (expiration de minuterie, famine)
  • Sortant : GuiNotification (sérialisée et envoyée aux clients GUI)

Les adaptateurs traduisent entre les ports et le domaine :

  • protocol::ai et protocol::gui parsent les octets bruts en commandes typées
  • protocol::gui::format sérialise les notifications typées en chaînes réseau
  • utils/actions/ fait correspondre les commandes typées aux mutations du domaine

La règle critique : world/ n'importe rien depuis protocol/ ou network/. L'encodage réseau de Direction::North (entier 1) se trouve exclusivement dans protocol::gui::format::player::orientation_code. Le type domaine ne porte aucune connaissance du protocole.

Références :

  • Hexagonal Architecture - Alistair Cockburn (2005)
  • Ports and Adapters - Herberto Graca (2017)

Noyau fonctionnel, enveloppe impérative

Le patron de Gary Bernhardt (2012) structure le code autour de deux zones distinctes :

  • Noyau fonctionnel : fonctions pures sans effets de bord. Tous les parseurs (protocol::ai::parse, protocol::gui::parse, protocol::gui::format) se trouvent ici. Pour une entrée donnée, ils retournent une sortie. Pas de sockets, pas d'état, pas de globaux mutables.
  • Enveloppe impérative : code qui gère les effets de bord. Le réacteur, app.rs et utils/actions/ se trouvent ici. Ils mutent l'état du monde, écrivent sur les sockets et planifient les ticks.

Ce découpage rend le noyau fonctionnel trivialement testable (pas de mocks, pas de préparation, pas de nettoyage) et l'enveloppe impérative clairement délimitée.

Références :

  • Functional Core, Imperative Shell - Gary Bernhardt (2012)
  • Functional Core / Imperative Shell - Medium

Le Réacteur

La couche réseau est une boucle d'événements TCP mono-thread non bloquante. Elle gère de nombreux clients concurrents sans créer un thread par connexion, délimite les commandes par saut de ligne, tampon les octets de réponse et pilote l'horloge de jeu.

Source : server/src/network/

Le patron Réacteur

Le patron Réacteur a été formellement décrit par Douglas Schmidt en 1995. Son insight central : plutôt que de donner à chaque source d'E/S son propre thread, enregistrer toutes les sources auprès d'un démultiplexeur unique et le laisser appeler le bon handler quand une source est prête.

flowchart TD
    A["Enregistrer les handlers<br/>(Listener + Clients)"] --> B
    B["poll(fds, timeout)"] --> C{Prêt ?}
    C -->|"lisible/inscriptible"| D["Handler::on_event()"]
    C -->|"timeout"| E["Exécuter les ticks de jeu"]
    D --> F["Appliquer les commandes<br/>différées (register/remove/stop)"]
    F --> B
    E --> B

Le réacteur ne se bloque jamais en attendant un client spécifique. Si le client A est lent, les clients B et C continuent d'être servis. C'est l'avantage fondamental sur un modèle un-thread-par-client pour un serveur de jeu avec de nombreux spectateurs inactifs.

Références :

  • Reactor: An Object Behavioral Pattern - Douglas Schmidt (1995)
  • Reactor Pattern - Wikipedia
  • Understanding the Reactor Pattern - DZone

Pourquoi poll(2) et non epoll ou kqueue ?

libc::poll reçoit un tableau de structures pollfd et retourne quels descripteurs sont prêts. Il scanne tous les descripteurs de façon linéaire, donc la latence croît avec le nombre de clients connectés (O(n)). epoll (Linux) et kqueue (BSD/macOS) évitent cela en maintenant une liste de prêts côté noyau (O(1) par événement).

Pour un serveur Zappy avec des dizaines à une centaine de clients, le scan linéaire est négligeable. poll est conforme POSIX, possède une API plus simple et ne nécessite pas de couche d'abstraction spécifique à la plateforme. Le choix est délibéré : simplicité plutôt que scalabilité prématurée.

Types clés

Token

#![allow(unused)]
fn main() {
pub struct Token(pub usize);
}

Un Token est l'identifiant stable au niveau applicatif d'un handler dans le réacteur. Les descripteurs de fichier ne sont pas utilisés comme identités car l'OS peut réutiliser un numéro de descripteur après la fermeture d'un socket. Les tokens augmentent de façon monotone et ne sont jamais réutilisés, ce qui rend les références périmées détectables.

C'est une instance du patron Newtype : un usize portant un type distinct pour que le compilateur rejette l'utilisation d'un id de joueur ou d'une coordonnée de tuile à sa place.

Interest

#![allow(unused)]
fn main() {
pub enum Interest { Read, Write, ReadWrite }
}

Un handler déclare quels événements de disponibilité il souhaite. Un client sans rien à envoyer s'enregistre uniquement en Read. Lorsque des octets sont en file d'attente pour l'écriture, le réacteur le ré-enregistre en ReadWrite pour recevoir aussi les événements POLLOUT. Revenir à Read après le vidage évite une boucle occupée car les sockets TCP sont presque toujours inscriptibles.

Trait Handler

#![allow(unused)]
fn main() {
pub trait Handler {
    fn fd(&self) -> RawFd;
    fn interest(&self) -> Interest;
    fn on_event(&mut self, event: Event, ctx: &mut ReactorContext) -> io::Result<()>;
    // capacités optionnelles avec implémentations no-op par défaut :
    fn connected_event(&self, _token: Token) -> Option<NetworkEvent> { None }
    fn disconnected_event(&self, _token: Token) -> Option<NetworkEvent> { None }
    fn add_res_buf(&mut self, _data: &[u8]) -> bool { false }
    fn flush(&mut self) -> NetworkResult<()> { Ok(()) }
}
}

flush est appelée par Reactor::flush_and_close pour vider le tampon d'écriture vers le socket avant que le handler ne soit désenregistré. Cela garantit que les octets de réponse mis en file d'attente atteignent le client même lorsque la connexion est fermée immédiatement après l'envoi (par exemple, quand une équipe n'a plus de créneaux disponibles). Client implémente flush en appelant write_res_socket() de façon synchrone ; les autres handlers utilisent le no-op par défaut.

Le trait Handler découple le réacteur de la logique spécifique TCP. Un TcpListener, un Client, ou un futur pipe de minuterie s'insèrent tous dans la même collection. Les handlers sont stockés comme Box<dyn Handler>, un trait object Rust : différents types concrets partagent une HashMap, avec le bon on_event sélectionné au moment de l'exécution via une vtable.

Commandes différées

Pendant qu'on_event détient un emprunt mutable d'un handler, le réacteur ne peut pas être muté simultanément (le vérificateur d'emprunts de Rust l'impose). Ajouter ou supprimer un autre handler à l'intérieur d'on_event nécessiterait un second emprunt mutable du réacteur, que le compilateur rejette.

La solution : les handlers ajoutent des commandes à un ReactorContext que le réacteur traite après la fin du dispatch courant.

sequenceDiagram
    participant Reactor
    participant Handler
    participant Ctx as ReactorContext

    Reactor->>Handler: on_event(event, &mut ctx)
    Handler->>Ctx: ctx.register(new_handler)
    Handler->>Ctx: ctx.remove(old_token)
    Handler-->>Reactor: Ok(())
    Note over Reactor: dispatch terminé
    Reactor->>Reactor: appliquer les commandes différées
    Reactor->>Reactor: nouveau handler enregistré
    Reactor->>Reactor: ancien handler supprimé

Ce patron est une forme de file de commandes : les mutations structurelles sont exprimées comme des données, différées jusqu'à ce qu'il soit sûr de les appliquer. C'est à la fois une solution aux règles d'emprunt Rust et un principe de conception : le dispatch du handler est stable au sein d'une itération de la boucle d'événements.

Découpage en lignes

TCP est un flux d'octets. Un appel read peut livrer la moitié d'une commande, une commande entière, ou plusieurs commandes concaténées. Chaque Client accumule les octets dans un tampon request: Vec<u8> et appelle next_command après chaque lecture pour extraire les lignes complètes :

read #1: b"forw"
tampon : b"forw"              -> pas de ligne complète

read #2: b"ard\nleft\ninv"
tampon : b"forward\nleft\ninv"
  -> émettre "forward"
  -> émettre "left"
restant : b"inv"

Les fins de ligne Unix (\n) et DOS (\r\n) sont acceptées. Les octets de commande sont transmis à app.rs comme Vec<u8> bruts sans conversion UTF-8 ; les parseurs de protocole décident indépendamment si du texte valide est requis.

Le tampon de requête est plafonné à 4096 octets. Dépasser cette limite avant que le tampon ne se vide déconnecte le client, bornant l'utilisation mémoire pour les connexions mal configurées ou malveillantes.

RAII et nettoyage des sockets

Le modèle de possession de Rust fournit RAII (Resource Acquisition Is Initialization) gratuitement. Un Client possède son TcpStream. Lorsque le Client est supprimé de la HashMap du réacteur, l'implémentation de Drop ferme le descripteur de fichier automatiquement. Aucun appel explicite à close n'est nécessaire, et aucun socket ne peut fuir.

Planification des ticks de jeu

Le réacteur utilise le paramètre timeout de poll pour implémenter les ticks de jeu sans second thread. Après chaque itération de la boucle d'événements, il calcule le temps restant jusqu'au prochain tick et le passe comme timeout de poll :

poll(fds, timeout_ms = millis_jusqu_au_prochain_tick)
  • Si un événement réseau arrive en premier, poll retourne avant la fin du timeout. Le réacteur traite l'événement puis boucle avec un timeout plus court.
  • Si la deadline du tick arrive en premier, poll expire. Le réacteur appelle le callback de tick, avance le World et boucle.

Si le serveur prend du retard, il exécute les ticks manquants dans une boucle de rattrapage plafonnée à 50 par itération. Cela empêche un serveur très en retard d'affamer les E/S réseau.

Vue d'ensemble de la couche protocole

La couche protocole traduit entre les octets TCP bruts et les valeurs Rust typées. Elle comporte deux moitiés délibérément symétriques et indépendantes :

Les trois fonctions sont des fonctions pures : pour une entrée donnée, elles retournent une sortie, ne mutent rien et ne causent aucun effet de bord. Elles sont donc trivialement testables et impossibles à mal utiliser.

Principes de conception partagés

Parse, Don't Validate

Formulé par Alexis King en 2019, ce principe stipule : plutôt que de passer une entrée brute avec une hypothèse de confiance, la parser une fois en un type qui rend les états invalides non représentables.

Appliqué dans toute cette couche : ni app.rs ni aucun handler d'action ne voit jamais un &str brut. Toute valeur qui franchit la frontière de parsage est soit une AiCommand / GuiCommand typée, soit une erreur typée. L'appelant ne peut pas traiter accidentellement une coordonnée Y de tuile comme un id de joueur.

Référence : Parse, don't validate - Alexis King (2019)

Patron Newtype

PlayerId(u32) et EggId(u32) sont des newtypes : des structs à un seul champ qui donnent à un u32 une identité de type distincte. Le compilateur rejette le passage de l'un là où l'autre est attendu, sans coût à l'exécution.

Références :

  • New Type Idiom - Rust By Example
  • Newtype - Rust Design Patterns
  • Item 6: Embrace the newtype pattern - Effective Rust

Pattern matching exhaustif

Le match de Rust sur un enum doit couvrir chaque variante. Ajouter une nouvelle variante GuiNotification sans mettre à jour format() est une erreur de compilation, pas une surprise à l'exécution. Cette complétude imposée par le compilateur élimine toute une catégorie de bugs de protocole.

Référence : Pattern and exhaustiveness checking - Rust Compiler Development Guide

Handshake de connexion

Avant qu'un client soit classifié comme Ai, il est Unknown. La première ligne qu'il envoie détermine son type :

stateDiagram-v2
    [*] --> Unknown: TCP connecté, WELCOME\n envoyé
    Unknown --> Gui: première ligne == "GRAPHIC"
    Unknown --> Ai: première ligne == nom d'équipe valide avec créneau disponible
    Unknown --> [*]: équipe inconnue / pas de créneau / pas d'œuf
    Ai --> Ai: commandes suivantes mises en file
    Gui --> Gui: requêtes GUI traitées

Lors d'une promotion IA réussie, le serveur :

  1. Choisit un œuf aléatoire dans l'équipe.
  2. Crée un Player à la position de l'œuf.
  3. Enregistre le mapping Token -> PlayerId dans State.
  4. Répond avec remaining_slots\n puis width height\n.
  5. Diffuse pnw #id X Y O L team\n à tous les clients GUI.
  6. Diffuse ebo #egg_id\n à tous les clients GUI (œuf éclos).

Équipe pleine : Lorsque spawn_player_from_team_egg retourne NoSlotsAvailable, le serveur envoie 0\n puis W H\n (zéro créneaux + dimensions), vide de façon synchrone via flush_and_close, et déconnecte le client.

Équipe inconnue : Le serveur envoie ko\n et ferme la connexion immédiatement sans envoyer le nombre de créneaux ni les dimensions.

Patrons de conception

Parseur prédictif LL(1)

Le parseur est un parseur prédictif LL(1) (gauche-à-droite, dérivation la plus à gauche, 1 token de lookahead). Il lit un token (le nom de la commande) et sait immédiatement quelle branche prendre. La grammaire IA de Zappy n'a ni ambiguïté ni récursion, donc un match plat sur le nom de commande est suffisant.

flowchart TD
    INPUT["'Take food'"] --> LEXER["Tokens::next_str()"]
    LEXER --> CMD{"nom de commande ?"}
    CMD -->|"Forward"| FWD["Ok(AiCommand::Forward)"]
    CMD -->|"Take"| RES["Tokens::next_str() = food"]
    RES --> KIND{"ResourceKind ?"}
    KIND -->|"food"| TAKE["Ok(AiCommand::Take(Food))"]
    KIND -->|"diamond"| ERR["Err(InvalidResource)"]
    CMD -->|"inconnu"| UNK["Err(UnknownCommand)"]

Curseur zéro-copie

La struct Tokens<'a> détient une tranche &'a str qui rétrécit au fur et à mesure que les tokens sont consommés. Les tokens retournés sont aussi des tranches &'a str empruntées depuis l'entrée originale. Aucune allocation de String n'a lieu sur le chemin nominal.

#![allow(unused)]
fn main() {
pub struct Tokens<'a> { rest: &'a str }
}

La durée de vie 'a lie chaque token retourné au tampon d'entrée original. Si l'entrée est allouée sur la pile ou possédée par l'appelant, aucune allocation tas n'est nécessaire pour parser une commande complète.

Références :

  • Rust: The joy of safe zero-copy parsers - ITNEXT
  • How to Create Zero-Copy Parsers in Rust - OneUptime Blog

Erreur comme donnée

ParseError est un enum typé. Chaque variante encode exactement un mode d'échec avec tout le contexte nécessaire pour agir dessus :

#![allow(unused)]
fn main() {
pub enum ParseError {
    UnknownCommand(Box<str>),   // le mauvais token pour le diagnostic
    MissingArgument,
    InvalidResource,
    TrailingInput,
}
}

Box<str> dans UnknownCommand évite une allocation à chaque parse de commande valide : l'allocation n'a lieu que lorsque le parsage a déjà échoué. L'appelant utilise un match exhaustif pour décider de la réponse (envoyer ko\n, journaliser, fermer la connexion) sans réinspecter la chaîne brute.

Philosophie de gestion des erreurs

Le parseur utilise ? partout. La première erreur termine le parsage et se propage vers handle_command.rs, qui envoie ko\n au client et laisse la file de commandes en attente inchangée.

unwrap() et expect() sont interdits dans tout code hors test. Chaque opération faillible propage son erreur vers le haut. Cela préserve l'information : l'appelant peut distinguer un argument manquant d'une commande inconnue et répondre de façon appropriée.

Séparation du lexage et du parsage

Deux étapes sont maintenues délibérément séparées :

  • Lexage (lexer.rs) : convertit &str en un flux de tokens typés via un curseur zéro-copie. Pas d'allocation tas sur le chemin nominal.
  • Parsage (parse.rs) : convertit le flux de tokens en GuiCommand. Le nom de la commande est le seul token de lookahead.

Ajouter une nouvelle commande ne nécessite que deux changements : une nouvelle variante dans GuiCommand et un nouveau bras de match dans parse(). Le lexer ne change jamais pour de nouvelles commandes.

Patrons de conception

Fonction pure

La fonction format n'a aucun effet de bord observable. C'est l'exemple canonique d'un composant de noyau fonctionnel : pour une notification typée donnée, elle retourne toujours la même chaîne. Les tests ne nécessitent ni mocks, ni préparation, ni nettoyage.

Si une mauvaise chaîne atteint un client GUI, toute la chaîne d'appel se réduit à un appel de fonction et une valeur d'entrée. Le débogage est trivialement délimité.

Référence : Functional Core, Imperative Shell - Gary Bernhardt (2012)

Dispatch exhaustif

Le match de Rust sur GuiNotification doit couvrir chaque variante. Ajouter un nouveau type de notification à l'enum et oublier d'ajouter le bras de format est une erreur de compilation. Le compilateur agit comme garant d'exhaustivité sur l'ensemble du protocole.

Masquage de l'information via pub(super)

Chaque fonction helper dans format/player.rs et format/world.rs est déclarée pub(super) : visible uniquement par format/mod.rs. Aucun code externe ne peut appeler directement player::player_death(...). Les détails du format réseau (entiers d'orientation, indices de ressources, préfixe #) sont des décisions internes cachées derrière la seule fonction publique format().

Si le protocole change l'encodage d'orientation de 1-4 vers des lettres cardinales, seul format/player.rs::orientation_code change. Tous les appelants restent intacts.

Référence : On the criteria to be used in decomposing systems into modules - David Parnas (1972)

Éviter les chaînes typées en dur

Le moteur de jeu construit une GuiNotification::PlayerPosition typée avec un PlayerId, une paire u32 x/y et un enum Orientation. Il ne construit jamais directement une chaîne "ppo #1 3 4 2\n". L'encodage des valeurs du domaine vers les entiers réseau se fait en un seul endroit et n'est jamais dupliqué.

C'est le complément côté sortie de Parse, Don't Validate : Format, Don't Encode.

Construction incrémentale de chaîne (IncantationStart)

IncantationStart porte une liste de longueur variable d'identifiants de joueurs participants. Plutôt que de collecter les ids dans un Vec<String> intermédiaire et de les joindre, le helper ajoute chaque id directement au tampon de sortie avec push_str :

    output.push('#');

Une seule allocation de String croît en place au lieu de créer et jeter plusieurs chaînes intermédiaires. C'est la même approche que StringBuilder en Java ou strings.Builder en Go.

Patrons de conception

Propriétaire mutable unique

Tout l'état de jeu réside dans World. Pas de propriété partagée (Arc, Mutex), pas de canaux, pas de threads en arrière-plan. La boucle d'événements détient une valeur World et la mute en appelant advance_tick une fois par unité de temps.

Cette approche élimine toute une classe de bugs de concurrence. Un &mut World en Rust est une référence mutable exclusive ; le vérificateur d'emprunts garantit qu'aucun autre code ne peut lire ou écrire l'état du monde pendant qu'advance_tick s'exécute.

Colocalisation du minuteur d'action

Chaque Player détient son propre action_ticks_remaining: u32. L'alternative (un HashMap<PlayerId, u32> dans World) nécessiterait que deux structures restent synchronisées à chaque suppression d'un joueur.

Garder le minuteur sur le joueur rend la suppression triviale : supprimer le joueur de world.players efface automatiquement le minuteur.

Déterminisme du respawn

#![allow(unused)]
fn main() {
if self.tick % RESPAWN_PERIOD == 0 { ... }   // déclenche à 20, 40, 60, ...
}

Le respawn se déclenche aux multiples absolus de 20, pas 20 ticks après le dernier déclenchement. Si le serveur rattrape un retard, plusieurs respawns manqués s'exécutent séquentiellement mais aux numéros de tick corrects. Le comportement est déterministe et indépendant de l'heure murale.

Modèle de créneaux initiaux

World::new appelle Team::new(name, 0) puis team.add_egg(id) une fois par créneau client. Cela garantit que available_slots est toujours égal au nombre d'œufs sur la carte. Chaque connexion passe par le chemin remove_egg, qui gère à la fois la comptabilité des créneaux et la recherche de position de l'œuf en une seule opération.

Système de temps

Le serveur opère en unités de temps. Une unité de temps = 1 / freq secondes. Le réacteur appelle advance_tick une fois par unité de temps.

    (y as usize) * (self.width as usize) + (x as usize)
}

Arithmétique toroïdale

Le déplacement utilise des deltas signés appliqués à des coordonnées non signées. La soustraction naïve déborde ; un seul % retourne des valeurs négatives en Rust. La solution utilise des intermédiaires i64 et rem_euclid :

#![allow(unused)]
fn main() {
pub fn offset(&self, x: u32, y: u32, dx: i32, dy: i32) -> (u32, u32) {
    let nx = ((x as i64 + dx as i64).rem_euclid(self.width as i64)) as u32;
    let ny = ((y as i64 + dy as i64).rem_euclid(self.height as i64)) as u32;
    (nx, ny)
}
}

rem_euclid retourne toujours une valeur non négative, donc l'enveloppement au-delà du bord gauche ou supérieur fonctionne correctement :

(-1).rem_euclid(10) == 9   // enveloppe vers le bord droit
(-1) % 10           == -1  // incorrect pour la sémantique toroïdale

flowchart LR
    A["Compter toutes les ressources<br/>sur la carte"] --> B["Calculer le déficit<br/>= cible - courant"]
    B --> C{déficit > 0 ?}
    C -->|oui| D["Placer les unités<br/>manquantes aléatoirement"]
    C -->|non| E["No-op"]
    D --> F["Retourner les positions<br/>de tuiles modifiées"]

Cette conception est idempotente : appeler respawn deux fois quand la carte est pleine ne change rien et retourne une liste vide. Le coût total est proportionnel au déficit, pas à la cible complète.

Générateur congruentiel linéaire

Rng utilise les constantes LCG MMIX de Knuth (multiplicateur 6364136223846793005, incrément 1442695040888963407) avec arithmétique enveloppante u64. Deux générateurs avec la même graine produisent des séquences identiques, rendant les parties reproductibles.

Les 32 bits supérieurs de chaque étape sont utilisés pour next_below afin d'exploiter les meilleures propriétés statistiques des bits de poids fort dans un LCG (les bits de poids faible dans un LCG standard ont des périodes plus courtes).

Service de domaine : take_resource / drop_resource

take_resource et drop_resource opèrent chacun sur une Tile et un Player simultanément. Placer cette logique sur l'un ou l'autre type créerait une importation dans le mauvais sens. Les fonctions libres sont le bon choix pour les opérations qui "n'appartiennent pas naturellement à un seul type" :

#![allow(unused)]
fn main() {
take_resource(&mut tile, &mut player, kind)?;  // tuile -> joueur
drop_resource(&mut tile, &mut player, kind)?;  // joueur -> tuile
}

Les deux délèguent à Resources::take et Resources::add, préservant l'atomicité en cas d'échec.

Joueur

Source : server/src/world/player/

Player est l'entité centrale du domaine Zappy. Il possède une identité unique (PlayerId), un état mutable et des invariants comportementaux appliqués par son API plutôt que par la discipline de l'appelant.

Structure

#![allow(unused)]
fn main() {

    pub id: PlayerId,
    pub x: u32,
    pub y: u32,

    pub level: u8,

food_ticks_remaining est privé. Seul tick_food() peut y accéder, ce qui garantit l'invariant : pour tout joueur vivant, ce compteur est toujours dans [1, 126].

Patron Entité

Une entité de domaine possède une identité unique et un état mutable. PlayerId(u32) est l'identité. Deux joueurs aux mêmes coordonnées mais avec des ids différents sont des entités distinctes ; deux joueurs avec le même id à des coordonnées différentes sont la même entité dans des états différents.

Le patron Entité est mis en contraste avec les Objets Valeur (comme Direction et Resources), qui n'ont pas d'identité et sont égaux quand tous leurs champs sont égaux.

Référence : Evans Classification - Martin Fowler

Direction : objet valeur

#![allow(unused)]
fn main() {

Direction dérive Copy et est passée par valeur. Les méthodes de rotation retournent une nouvelle Direction plutôt que de muter self :

Le chaînage est naturel car chaque appel retourne le même type :

to_delta() retourne la paire (dx, dy) pour un pas en avant. La convention de coordonnées (Nord = (0, -1), Sud = (0, +1)) est encodée dans les tests.

La file comme contrat de protocole

L'œuf comme objet valeur

#![allow(unused)]

Egg n'a pas de méthodes mutables. Quand un œuf change de statut (éclot ou est détruit), l'appelant le supprime du monde et de l'équipe. Il n'y a pas de mutation en place d'un œuf existant.

C'est le patron Objet Valeur du DDD : l'œuf n'est pas défini par la continuité de son identité mais par ses attributs. EggId est l'identifiant ; l'œuf lui-même est une donnée jetable.

Référence : Evans Classification - Martin Fowler

Pourquoi Team et Egg sont des types séparés

Team ne stocke que des EggId, pas des valeurs Egg complètes. La position et le nom d'équipe résident dans Egg, que le World possède aux côtés de Player. Le lien est l'identifiant :

Tile::players   Vec<PlayerId> --> Player dans World.players
Team::eggs      Vec<EggId>    --> Egg    dans World.eggs

Stocker des valeurs Egg complètes dans Team couplerait la politique d'accès (comptage des créneaux) avec la localisation physique (position sur la tuile). Ces deux préoccupations évoluent indépendamment.

Encapsulation par invariant

available_slots et eggs sont privés. Les méthodes publiques maintiennent l'invariant de façon atomique :

  • add_egg : enregistre l'id de l'œuf et incrémente available_slots.
  • remove_egg : supprime l'id et décrémente available_slots avec saturating_sub (ne descend jamais sous zéro).
  • consume_slot : décrémente available_slots d'un mais retourne Err(NoSlotsAvailable) avant de décrémenter si déjà à zéro.

Il n'existe aucun chemin qui laisse le compteur incohérent avec la liste d'œufs.

Boucle d'exécution des actions

Source : server/src/utils/actions/

Lorsque World::advance_tick émet WorldEvent::ActionReady { player_id, action }, tick_events.rs appelle actions::execute(reactor, state, world, player_id, action). C'est la frontière entre le système de temps et la logique de jeu.

execute résout le Token à partir du player_id via state.token_for(player_id) avant de construire l'ActionContext et de dispatcher. Si le joueur n'a pas de token associé (déjà déconnecté), l'action est silencieusement ignorée.

ActionContext

Toutes les fonctions d'action reçoivent un ActionContext<'a> plutôt que trois paramètres séparés :

#![allow(unused)]
fn main() {
pub struct ActionContext<'a> {
    pub reactor: &'a mut Reactor,
    pub state: &'a mut State,
    pub world: &'a mut World,
}
}

Cela réduit chaque signature d'action de 5-6 arguments à 3-4, et regroupe les trois références mutables dont chaque handler a besoin dans une struct nommée. La décomposition des emprunts au niveau des champs en Rust permet d'accéder à ctx.reactor et ctx.state simultanément car ce sont des champs distincts de la même struct.

Déplacement

Forward calcule la nouvelle position avec Direction::to_delta et Map::offset (enveloppement toroïdal), met à jour les listes de joueurs des tuiles, met à jour la struct du joueur, et diffuse ppo à tous les clients GUI.

Look

Look construit la liste de tuiles visibles en fonction du niveau et de l'orientation du joueur. Au niveau L, le joueur voit (L+1)^2 tuiles disposées en diamant s'élargissant vers l'avant : la tuile actuelle, puis L rangées vers l'avant chacune plus large de 2 tuiles.

Niveau 1 : [soi] [avant-gauche, avant, avant-droite]  (4 tuiles)
Niveau 2 : [soi] [3 tuiles à la rangée 1] [5 tuiles à la rangée 2]  (9 tuiles)

Chaque tuile est formatée comme une liste séparée par des espaces de son contenu : player, food, linemate, etc.

Broadcast

Broadcast calcule la direction K (1-8) du point de vue de chaque récepteur en utilisant une géométrie toroïdale par chemin le plus court. K=0 signifie que l'émetteur et le récepteur partagent la même tuile. Le récepteur obtient message K, texte\n ; l'émetteur obtient ok\n. La notification pbc va à tous les clients GUI.

Eject

Eject pousse tous les joueurs et détruit tous les œufs sur la tuile du lanceur dans la direction du lanceur. Les joueurs poussés se déplacent vers la tuile adjacente dans cette direction (toroïdale). Chaque joueur poussé reçoit eject: K\n où K est la direction de poussée. Les clients GUI reçoivent pex pour chaque joueur poussé et edi pour chaque œuf détruit.

Fork

Fork alloue un nouvel EggId, crée un Egg à la position actuelle du joueur, l'enregistre auprès de l'équipe (incrémentant available_slots), et envoie pfk + enw à tous les clients GUI. L'œuf persiste jusqu'à ce qu'un nouveau client IA en éclose ou qu'un Eject le détruise.

Commandes de ressources

Take déplace une unité de la ressource nommée de la tuile vers l'inventaire du joueur, envoie ok\n ou ko\n, et en cas de succès diffuse pgt et le bct mis à jour à tous les clients GUI. Set fait l'inverse.

Les deux utilisent les fonctions libres take_resource et drop_resource (patron service de domaine) pour opérer à la fois sur la Tile et le Player de façon atomique.

Incantation

Sources : server/src/utils/actions/incantation/, server/src/utils/commands/handle_ai_command.rs

L'incantation est le rituel d'élévation. Un groupe de joueurs du même niveau sur la même tuile peut collectivement augmenter son niveau en consommant des pierres spécifiques. Le rituel prend 300 unités de temps (300/f secondes).

Conception en deux phases

L'incantation utilise un commit en deux phases : les préconditions sont vérifiées immédiatement au moment de la mise en file (Phase 1), et le rituel s'exécute après le décompte de 300 ticks (Phase 2). Cela empêche un joueur de mettre en file une incantation qui n'aurait aucune chance de réussir.

Collecte des participants

#![allow(unused)]
fn main() {
pub(crate) fn collect_participants(
    world: &World,
    x: u32,
    y: u32,
    level: u8,
) -> Vec<PlayerId> {
    world.map.get(x, y).players.iter()
        .filter(|&&pid| {
            world.players.get(&pid)
                .is_some_and(|p| p.level == level && !p.frozen)
        })
        .copied()
        .collect()
}
}

Seuls les joueurs sur la même tuile, au même niveau que l'initiateur, et pas déjà gelés dans une autre incantation sont éligibles. Le joueur initiant est toujours inclus (il est sur la tuile et pas encore gelé au moment de la collecte).

Consommation des ressources

tile.resources.consume(&req.resources) soustrait toutes les pierres requises en un seul appel après que has_enough confirme leur présence. C'est une opération atomique : si has_enough retourne vrai, consume ne paniquera pas.

Drapeau de gel

player.frozen est fixé à true lors de la Phase 1 (moment de la mise en file), immédiatement après la confirmation des conditions et la diffusion de pic. Cela empêche les participants d'exécuter de nouvelles actions pendant le décompte du rituel.

Un joueur gelé peut toujours recevoir des commandes - elles sont tamponnées dans la file d'actions - mais tick_action n'exécute aucune action tant que frozen == true. À la fin du rituel (succès ou échec), tous les participants sont dégelés et leurs actions en file reprennent normalement.

Condition de victoire

Source : server/src/utils/actions/incantation/victory.rs

Après chaque incantation réussie, check_victory analyse tous les joueurs pour vérifier la condition de victoire.

Condition

La partie se termine lorsque six joueurs ou plus de la même équipe détiennent simultanément le niveau 8 (MAX_LEVEL).

#![allow(unused)]
fn main() {

}

Diffusion et arrêt

#![allow(unused)]
fn main() {

// réseau : "seg nom_equipe\n"
}

seg est diffusé à tous les clients GUI connectés via broadcast_gui. Les clients IA ne reçoivent pas seg directement ; leurs sockets sont fermés quand le réacteur s'arrête.

Après la diffusion, check_victory appelle ctx.reactor.stop(), qui fixe le drapeau interne running du réacteur à false. La boucle d'événements se termine proprement après l'itération courante, fermant tous les handlers enregistrés.

Pourquoi vérifier après chaque incantation ?

Le seul moyen pour un joueur d'atteindre le niveau 8 est une incantation réussie au niveau 7. Vérifier la condition de victoire après chaque incantation réussie garantit que la vérification se déclenche au plus tôt possible, sans surcharge de sondage lors des ticks où aucune élévation n'a eu lieu.

Patrons de conception

Parse, Don't Validate

Le moteur de jeu ne touche jamais une chaîne d'argument brute. Il reçoit un ServerArgs avec des champs typés. La seule frontière de parsage est ServerArgs::from_args(). Tout ce qui la franchit est soit une struct entièrement typée, soit une ArgsError typée.

Référence : Parse, don't validate - Alexis King (2019)

Scan de tokens prédictif (LL(1))

Les arguments sont consommés de gauche à droite avec un curseur d'index. Chaque token est examiné une fois : s'il commence par -, c'est un flag ; sinon c'est une valeur pour le flag courant. Pas de retour arrière. C'est le même patron LL(1) utilisé dans le parseur de commandes GUI, appliqué à une liste clé-valeur plate.

Helper générique : next_parsed<T>

Une seule fonction générique remplace ce qui serait autrement deux fonctions identiques next_u16 et next_u32 :

#![allow(unused)]
fn main() {
fn next_parsed<T: FromStr>(flag: &str, args: &[String], idx: &mut usize)
    -> Result<T, ArgsError>
}

Le paramètre de type est inféré depuis le contexte. La contrainte T: FromStr est la borne minimale et correcte : la fonction n'a besoin que d'appeler str::parse::<T>().

Référence : std::str::FromStr - Rust Standard Library

Le comportement appartient à son type

from_args est une méthode constructeur sur ServerArgs, pas une fonction libre :

#![allow(unused)]
fn main() {
let config = ServerArgs::from_args(&raw_args)?;
}

Le site d'appel se lit comme une intention. Une fonction libre parse_args(&raw_args) ne dit rien sur ce qu'elle produit. La forme de méthode est auto-documentée.

Variantes d'erreur

VarianteCause
UnknownFlag(String)Un token -x n'était pas un flag reconnu
MissingValue(&str)Un flag était présent mais aucune valeur ne suivait
InvalidValue { flag, raw }Une valeur n'a pas pu être parsée comme le type attendu
MissingFlag(&str)Un flag requis était absent
NoTeamNames-n était présent mais aucun nom ne suivait
ZeroValue(&str)Un flag numérique a donné zéro

La première erreur rencontrée termine immédiatement le parsage. Il n'y a pas d'accumulation d'erreurs ni de succès partiel.

Le flag -n

-n est le seul flag à longueur variable. Il collecte tous les tokens consécutifs qui ne commencent pas par - comme noms d'équipes. La collecte s'arrête au prochain flag ou à la fin de l'entrée :

# Deux noms d'équipes collectés, puis -c reconnu comme prochain flag
zappy_server -n red blue -c 2 -p 4242 -x 10 -y 10 -f 100

Les noms d'équipes ne doivent pas commencer par -. Cela correspond à la spécification qui traite les noms d'équipes comme de simples identifiants.

Référence des patrons de conception

Ce chapitre catalogue tous les patrons de conception utilisés dans le serveur, avec des définitions, des justifications et des liens vers des sources faisant autorité. Les patrons sont ordonnés par catégorie.

Patrons architecturaux

Architecture hexagonale (ports et adaptateurs)

Ce que c'est : Le noyau applicatif (domaine) est entouré de ports (interfaces) et d'adaptateurs (implémentations). Le noyau ne dépend jamais de l'infrastructure.

Où utilisé : L'ensemble du serveur. world/ n'importe rien depuis network/ ou protocol/. L'encodage réseau de Direction::North (entier 1) se trouve exclusivement dans protocol/gui/format/player.rs.

Pourquoi : Le domaine peut être testé, évolué et raisonné sans aucune configuration réseau ou protocole. Les tests pour World, Player et Map ne nécessitent pas de socket TCP.

Sources :

  • Hexagonal Architecture - Alistair Cockburn (2005)
  • Ports and Adapters - Herberto Graca (2017)

Noyau fonctionnel, enveloppe impérative

Ce que c'est : Le code est divisé en un noyau interne pur (sans effets de bord) et une enveloppe externe impure (E/S, mutation).

Où utilisé : Les trois parseurs et le sérialiseur GUI sont des fonctions pures. app.rs, le réacteur et utils/actions/ constituent l'enveloppe impérative.

Pourquoi : Le noyau pur est trivialement testable. L'enveloppe est petite et clairement délimitée. Les bugs dans la couche réseau ne peuvent pas corrompre le comportement du parseur.

Sources :

  • Functional Core, Imperative Shell - Gary Bernhardt (2012)
  • Patterns of Functional Programming - Javier Casas

Patrons de concurrence et d'E/S

Patron Réacteur

Ce que c'est : Un seul thread démultiplexe les événements E/S via une facilité de sondage OS et dispatche chaque événement au handler enregistré.

Où utilisé : server/src/network/reactor.rs. Un réacteur gère toutes les connexions TCP et l'horloge de jeu.

Pourquoi : Évite un thread par client. Adapté à un serveur de jeu avec de nombreux observateurs GUI inactifs et un nombre borné de joueurs IA.

Sources :

  • Reactor: An Object Behavioral Pattern - Douglas Schmidt (1995)
  • Reactor Pattern - Wikipedia

Patrons de domaine (DDD)

Entité

Ce que c'est : Un objet défini par son identité unique plutôt que par ses valeurs d'attributs. Deux entités avec les mêmes attributs mais des ids différents sont distinctes.

Où utilisé : Player (identifié par PlayerId). La struct du joueur a un état mutable ; son identité est stable à travers toutes les mutations.

Sources :

  • Evans Classification - Martin Fowler
  • Domain-Driven Design - Eric Evans (2003)

Objet valeur

Ce que c'est : Un objet sans identité conceptuelle, défini entièrement par ses valeurs d'attributs. Deux objets valeur avec les mêmes attributs sont interchangeables.

Où utilisé :

  • Direction (Nord/Est/Sud/Ouest - dérive Copy, les méthodes retournent de nouvelles valeurs)
  • Resources (sept compteurs - dérive Default, Clone, PartialEq)
  • Egg (position + nom d'équipe - immuable après création, supprimé plutôt que muté)

Sources :

  • Evans Classification - Martin Fowler
  • Value Object - refactoring.guru

Racine d'agrégat

Ce que c'est : Un ensemble d'objets de domaine accessible via un seul point d'entrée qui applique tous les invariants pour l'ensemble.

Où utilisé : World est la racine d'agrégat. Tout l'état de jeu (carte, joueurs, œufs, équipes) est accessible via une seule instance World. La boucle d'événements détient une référence mutable exclusive sur World.

Sources :

  • Aggregate - Martin Fowler

Service de domaine (fonction libre)

Ce que c'est : Une opération qui n'appartient naturellement à aucune entité ou objet valeur unique, implémentée comme une fonction libre.

Où utilisé : take_resource(tile, player, kind) et drop_resource(tile, player, kind) opèrent sur une Tile et un Player simultanément. Placer cette logique sur l'un ou l'autre type créerait une dépendance d'import indésirable.

Sources :

  • Domain Service - Domain-Driven Design Reference

Patrons comportementaux

Patron Commande

Ce que c'est : Une opération est encapsulée comme un objet, permettant la paramétrisation, la mise en file et l'exécution différée.

Où utilisé : L'enum Action. Chaque commande IA est une valeur de première classe stockée dans ActionQueue. time_cost() est une méthode pure sur la valeur. La logique d'exécution réside dans utils/actions/, pas dans l'action elle-même.

Sources :

  • Command Pattern - Refactoring Guru
  • Command - Gang of Four (1994)

Patrons de parsage

Parse, Don't Validate

Ce que c'est : Au lieu de valider une entrée brute et de la passer avec une hypothèse de confiance, la parser une fois dans un type qui rend les états invalides non représentables.

Où utilisé : Chaque parseur du serveur (protocol::ai::parse, protocol::gui::parse, cli::ServerArgs::from_args). Le moteur de jeu ne reçoit jamais une chaîne brute pour une commande ou un flag.

Sources :

  • Parse, don't validate - Alexis King (2019)
  • Parse, Don't Validate - DevIQ

Parseur prédictif LL(1)

Ce que c'est : Un parseur descendant qui lit un token de lookahead et sélectionne immédiatement la règle de production correcte sans retour arrière.

Où utilisé : protocol::ai::parse, protocol::gui::parse, cli::ServerArgs::from_args. La grammaire de chaque protocole est plate et non ambiguë ; un token de lookahead est toujours suffisant.

Sources :

  • Classification of Top Down Parsers - GeeksforGeeks
  • LL(1) grammars - UW Madison

Curseur zéro-copie

Ce que c'est : Un parseur parcourt l'entrée en avançant un pointeur de référence ou de tranche, sans jamais allouer une copie des octets sous-jacents.

Où utilisé : Tokens<'a> dans protocol::ai::lexer et protocol::gui::lexer. La durée de vie 'a lie les tokens retournés au tampon d'entrée original.

Sources :

  • Rust: The joy of safe zero-copy parsers - ITNEXT
  • How to Create Zero-Copy Parsers in Rust - OneUptime

Patrons structuraux

Patron Newtype

Ce que c'est : Une struct à un seul champ qui enveloppe un primitif pour créer un type distinct sans surcharge à l'exécution.

Où utilisé : PlayerId(u32), EggId(u32), Token(usize). Le compilateur rejette le passage d'une coordonnée de tuile là où un id de joueur est attendu.

Sources :

  • New Type Idiom - Rust By Example
  • Newtype - Rust Design Patterns
  • Item 6: Embrace the newtype pattern - Effective Rust

Masquage de l'information (décomposition de Parnas)

Ce que c'est : Un module cache les décisions de conception susceptibles de changer derrière une interface stable. Seule l'interface est visible ; les internes ne le sont pas.

Où utilisé : format/player.rs et format/world.rs déclarent tous leurs helpers pub(super). Aucun code extérieur à format/mod.rs ne peut les appeler directement. L'encodage réseau pour les entiers d'orientation et les indices de ressources est un détail d'implémentation caché.

Sources :

  • On the criteria to be used in decomposing systems into modules - David Parnas (1972)
  • Visibility and privacy - The Rust Reference

Gestion de la mémoire et des ressources

RAII (Resource Acquisition Is Initialization)

Ce que c'est : Une ressource (mémoire, descripteur de fichier, socket) est liée à la durée de vie d'une valeur Rust. Supprimer la valeur libère la ressource.

Où utilisé : Client possède son TcpStream. Quand le Client est supprimé de la HashMap du réacteur, Rust appelle Drop sur le TcpStream, fermant automatiquement le descripteur de fichier. Aucun close explicite n'est nécessaire ; aucun socket ne peut fuir.

Sources :

  • RAII - Wikipedia
  • RAII - Rust By Example

Tampon plat (stockage 2D contigu)

Ce que c'est : Un tableau N-dimensionnel stocké en un seul bloc contigu de mémoire, indexé par une formule arithmétique.

Où utilisé : Map stocke toutes les tuiles dans un Vec<Tile> avec la formule index = y * largeur + x. L'alternative Vec<Vec<Tile>> a une indirection supplémentaire par ligne.

Sources :

  • Row- and column-major order - Wikipedia

Génération de nombres aléatoires

Générateur congruentiel linéaire (LCG)

Ce que c'est : Un générateur de nombres pseudo-aléatoires défini par la récurrence X_{n+1} = (a * X_n + c) mod m, où a, c, m sont des constantes soigneusement choisies.

Où utilisé : world::Rng utilise les constantes MMIX de Knuth. Deux générateurs avec la même graine produisent des séquences identiques, rendant l'initialisation de la carte reproductible.

Sources :

  • Linear congruential generator - Wikipedia
  • Knuth, The Art of Computer Programming Vol. 2 - Stanford
