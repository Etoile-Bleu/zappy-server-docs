Zappy Serveur

Joueur

Source : server/src/world/player/

Player est l'entité centrale du domaine Zappy. Il possède une identité unique (PlayerId), un état mutable et des invariants comportementaux appliqués par son API plutôt que par la discipline de l'appelant.

Structure

#![allow(unused)]
fn main() {
pub struct Player {
    pub id: PlayerId,
    pub x: u32,
    pub y: u32,
    pub direction: Direction,
    pub level: u8,
    pub inventory: Resources,
    pub actions: ActionQueue,
    pub frozen: bool,      // vrai pendant une incantation
    food_ticks_remaining: u32,   // privé
}
}

food_ticks_remaining est privé. Seul tick_food() peut y accéder, ce qui garantit l'invariant : pour tout joueur vivant, ce compteur est toujours dans [1, 126].

Patron Entité

Une entité de domaine possède une identité unique et un état mutable. PlayerId(u32) est l'identité. Deux joueurs aux mêmes coordonnées mais avec des ids différents sont des entités distinctes ; deux joueurs avec le même id à des coordonnées différentes sont la même entité dans des états différents.

Le patron Entité est mis en contraste avec les Objets Valeur (comme Direction et Resources), qui n'ont pas d'identité et sont égaux quand tous leurs champs sont égaux.

Référence : Evans Classification - Martin Fowler

Direction : objet valeur

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Direction { North, East, South, West }
}

Direction dérive Copy et est passée par valeur. Les méthodes de rotation retournent une nouvelle Direction plutôt que de muter self :

#![allow(unused)]
fn main() {
player.direction = player.direction.turn_right();
}

Le chaînage est naturel car chaque appel retourne le même type :

#![allow(unused)]
fn main() {
let facing_south = Direction::North.turn_right().turn_right();
}

to_delta() retourne la paire (dx, dy) pour un pas en avant. La convention de coordonnées (Nord = (0, -1), Sud = (0, +1)) est encodée dans les tests.

Modèle de nourriture à deux variables

La gestion de la nourriture utilise deux variables séparées :

  • inventory.food : pierres de nourriture transportées. Affichée par la commande Inventory et la notification GUI PlayerInventory.
  • food_ticks_remaining : décompte privé de 126 à 0. Quand il atteint 0, une pierre est consommée.
stateDiagram-v2
    direction LR
    [*] --> Vivant: food=10, ticks=126
    Vivant --> Vivant: tick_food() vrai (ticks 1..125)
    Vivant --> PierreCons: tick 126 - ticks=0, food 10->9, réinitialisation à 126
    PierreCons --> Vivant: continuer
    Vivant --> Mort: tick 1260 - ticks=0, food 1->0, retourne faux
    Mort --> [*]

La garantie de survie : un joueur fraîchement créé avec 10 unités de nourriture survit exactement 10 * 126 = 1260 ticks.

L'alternative (un seul compteur food_units * 126) produirait 1386 ticks pour 10 pierres initiales car le minuteur s'exécute avant la consommation de la première pierre. Le modèle à deux variables est correct par construction.

Patron Commande : ActionQueue

#![allow(unused)]
fn main() {
pub struct ActionQueue { actions: VecDeque<Action> }
}

Action est un enum fermé où chaque variante est une valeur de première classe :

#![allow(unused)]
fn main() {
pub enum Action {
    Forward, TurnRight, TurnLeft, Look, Inventory,
    Broadcast(String), ConnectNbr, Fork, Eject,
    Take(ResourceKind), Set(ResourceKind), Incantation,
}
}

time_cost() retourne le coût d'exécution sans aucun état mutable. Cela fait de la file une structure de données pure. La logique d'exécution réside dans utils/actions/, pas dans l'action elle-même.

#![allow(unused)]
fn main() {
let cost = action.time_cost();   // pur, sans effets de bord
player.enqueue_action(action);   // en file, non exécuté
}

La file comme contrat de protocole

ActionQueue encapsule un VecDeque<Action> avec une capacité maximale de 10. push retourne false quand la file est pleine plutôt que de paniquer ou de supprimer silencieusement. La spécification indique :

"Le client peut envoyer jusqu'à 10 requêtes consécutives sans aucune réponse. Au-delà de 10, le serveur ne les prend plus en compte."

La capacité est imposée par le type. Tout code qui appelle push gère le cas false explicitement.
