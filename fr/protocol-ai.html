Zappy Serveur

Protocole IA

Source : server/src/protocol/ai/

Le module de protocole IA transforme les lignes de commandes brutes en valeurs AiCommand typées. C'est un parseur pur : il ne journalise pas, ne mute pas l'état et n'écrit pas sur les sockets. Toutes les décisions sur ce qu'il faut faire d'une commande parsée appartiennent à handle_command.rs.

Structure des fichiers

server/src/protocol/ai/
    mod.rs       câblage du module et exports publics
    command.rs   enum AiCommand
    error.rs     enum ParseError
    lexer.rs     curseur Tokens sur la chaîne d'entrée
    parse.rs     point d'entrée parse()

Handshake de connexion

Avant qu'un client soit classifié comme Ai, il est Unknown. La première ligne qu'il envoie détermine son type :

stateDiagram-v2
    [*] --> Unknown: TCP connecté, WELCOME\n envoyé
    Unknown --> Gui: première ligne == "GRAPHIC"
    Unknown --> Ai: première ligne == nom d'équipe valide avec créneau disponible
    Unknown --> [*]: équipe inconnue / pas de créneau / pas d'œuf
    Ai --> Ai: commandes suivantes mises en file
    Gui --> Gui: requêtes GUI traitées

Lors d'une promotion IA réussie, le serveur :

  1. Choisit un œuf aléatoire dans l'équipe.
  2. Crée un Player à la position de l'œuf.
  3. Enregistre le mapping Token -> PlayerId dans State.
  4. Répond avec remaining_slots\n puis width height\n.
  5. Diffuse pnw #id X Y O L team\n à tous les clients GUI.
  6. Diffuse ebo #egg_id\n à tous les clients GUI (œuf éclos).

Équipe pleine : Lorsque spawn_player_from_team_egg retourne NoSlotsAvailable, le serveur envoie 0\n puis W H\n (zéro créneaux + dimensions), vide de façon synchrone via flush_and_close, et déconnecte le client.

Équipe inconnue : Le serveur envoie ko\n et ferme la connexion immédiatement sans envoyer le nombre de créneaux ni les dimensions.

Patrons de conception

Parseur prédictif LL(1)

Le parseur est un parseur prédictif LL(1) (gauche-à-droite, dérivation la plus à gauche, 1 token de lookahead). Il lit un token (le nom de la commande) et sait immédiatement quelle branche prendre. La grammaire IA de Zappy n'a ni ambiguïté ni récursion, donc un match plat sur le nom de commande est suffisant.

flowchart TD
    INPUT["'Take food'"] --> LEXER["Tokens::next_str()"]
    LEXER --> CMD{"nom de commande ?"}
    CMD -->|"Forward"| FWD["Ok(AiCommand::Forward)"]
    CMD -->|"Take"| RES["Tokens::next_str() = food"]
    RES --> KIND{"ResourceKind ?"}
    KIND -->|"food"| TAKE["Ok(AiCommand::Take(Food))"]
    KIND -->|"diamond"| ERR["Err(InvalidResource)"]
    CMD -->|"inconnu"| UNK["Err(UnknownCommand)"]

Curseur zéro-copie

La struct Tokens<'a> détient une tranche &'a str qui rétrécit au fur et à mesure que les tokens sont consommés. Les tokens retournés sont aussi des tranches &'a str empruntées depuis l'entrée originale. Aucune allocation de String n'a lieu sur le chemin nominal.

#![allow(unused)]
fn main() {
pub struct Tokens<'a> { rest: &'a str }
}

La durée de vie 'a lie chaque token retourné au tampon d'entrée original. Si l'entrée est allouée sur la pile ou possédée par l'appelant, aucune allocation tas n'est nécessaire pour parser une commande complète.

  • Rust: The joy of safe zero-copy parsers - ITNEXT
  • How to Create Zero-Copy Parsers in Rust - OneUptime Blog

Erreur comme donnée

ParseError est un enum typé. Chaque variante encode exactement un mode d'échec avec tout le contexte nécessaire pour agir dessus :

#![allow(unused)]
fn main() {
pub enum ParseError {
    UnknownCommand(Box<str>),   // le mauvais token pour le diagnostic
    MissingArgument,
    InvalidResource,
    TrailingInput,
}
}

Box<str> dans UnknownCommand évite une allocation à chaque parse de commande valide : l'allocation n'a lieu que lorsque le parsage a déjà échoué. L'appelant utilise un match exhaustif pour décider de la réponse (envoyer ko\n, journaliser, fermer la connexion) sans réinspecter la chaîne brute.

Philosophie de gestion des erreurs

Le parseur utilise ? partout. La première erreur termine le parsage et se propage vers handle_command.rs, qui envoie ko\n au client et laisse la file de commandes en attente inchangée.

unwrap() et expect() sont interdits dans tout code hors test. Chaque opération faillible propage son erreur vers le haut. Cela préserve l'information : l'appelant peut distinguer un argument manquant d'une commande inconnue et répondre de façon appropriée.
