Zappy Serveur

Le Réacteur

La couche réseau est une boucle d'événements TCP mono-thread non bloquante. Elle gère de nombreux clients concurrents sans créer un thread par connexion, délimite les commandes par saut de ligne, tampon les octets de réponse et pilote l'horloge de jeu.

Source : server/src/network/

Le patron Réacteur

Le patron Réacteur a été formellement décrit par Douglas Schmidt en 1995. Son insight central : plutôt que de donner à chaque source d'E/S son propre thread, enregistrer toutes les sources auprès d'un démultiplexeur unique et le laisser appeler le bon handler quand une source est prête.

flowchart TD
    A["Enregistrer les handlers<br/>(Listener + Clients)"] --> B
    B["poll(fds, timeout)"] --> C{Prêt ?}
    C -->|"lisible/inscriptible"| D["Handler::on_event()"]
    C -->|"timeout"| E["Exécuter les ticks de jeu"]
    D --> F["Appliquer les commandes<br/>différées (register/remove/stop)"]
    F --> B
    E --> B

Le réacteur ne se bloque jamais en attendant un client spécifique. Si le client A est lent, les clients B et C continuent d'être servis. C'est l'avantage fondamental sur un modèle un-thread-par-client pour un serveur de jeu avec de nombreux spectateurs inactifs.

Références :

  • Reactor: An Object Behavioral Pattern - Douglas Schmidt (1995)
  • Reactor Pattern - Wikipedia
  • Understanding the Reactor Pattern - DZone

Pourquoi poll(2) et non epoll ou kqueue ?

libc::poll reçoit un tableau de structures pollfd et retourne quels descripteurs sont prêts. Il scanne tous les descripteurs de façon linéaire, donc la latence croît avec le nombre de clients connectés (O(n)). epoll (Linux) et kqueue (BSD/macOS) évitent cela en maintenant une liste de prêts côté noyau (O(1) par événement).

Pour un serveur Zappy avec des dizaines à une centaine de clients, le scan linéaire est négligeable. poll est conforme POSIX, possède une API plus simple et ne nécessite pas de couche d'abstraction spécifique à la plateforme. Le choix est délibéré : simplicité plutôt que scalabilité prématurée.

Références :

  • poll(2) - Linux man pages
  • Comparing poll vs epoll - Cloudflare Blog

Types clés

Token

#![allow(unused)]
fn main() {
pub struct Token(pub usize);
}

Un Token est l'identifiant stable au niveau applicatif d'un handler dans le réacteur. Les descripteurs de fichier ne sont pas utilisés comme identités car l'OS peut réutiliser un numéro de descripteur après la fermeture d'un socket. Les tokens augmentent de façon monotone et ne sont jamais réutilisés, ce qui rend les références périmées détectables.

C'est une instance du patron Newtype : un usize portant un type distinct pour que le compilateur rejette l'utilisation d'un id de joueur ou d'une coordonnée de tuile à sa place.

Interest

#![allow(unused)]
fn main() {
pub enum Interest { Read, Write, ReadWrite }
}

Un handler déclare quels événements de disponibilité il souhaite. Un client sans rien à envoyer s'enregistre uniquement en Read. Lorsque des octets sont en file d'attente pour l'écriture, le réacteur le ré-enregistre en ReadWrite pour recevoir aussi les événements POLLOUT. Revenir à Read après le vidage évite une boucle occupée car les sockets TCP sont presque toujours inscriptibles.

Trait Handler

#![allow(unused)]
fn main() {
pub trait Handler {
    fn fd(&self) -> RawFd;
    fn interest(&self) -> Interest;
    fn on_event(&mut self, event: Event, ctx: &mut ReactorContext) -> io::Result<()>;
    // capacités optionnelles avec implémentations no-op par défaut :
    fn connected_event(&self, _token: Token) -> Option<NetworkEvent> { None }
    fn disconnected_event(&self, _token: Token) -> Option<NetworkEvent> { None }
    fn add_res_buf(&mut self, _data: &[u8]) -> bool { false }
    fn flush(&mut self) -> NetworkResult<()> { Ok(()) }
}
}

flush est appelée par Reactor::flush_and_close pour vider le tampon d'écriture vers le socket avant que le handler ne soit désenregistré. Cela garantit que les octets de réponse mis en file d'attente atteignent le client même lorsque la connexion est fermée immédiatement après l'envoi (par exemple, quand une équipe n'a plus de créneaux disponibles). Client implémente flush en appelant write_res_socket() de façon synchrone ; les autres handlers utilisent le no-op par défaut.

Le trait Handler découple le réacteur de la logique spécifique TCP. Un TcpListener, un Client, ou un futur pipe de minuterie s'insèrent tous dans la même collection. Les handlers sont stockés comme Box<dyn Handler>, un trait object Rust : différents types concrets partagent une HashMap, avec le bon on_event sélectionné au moment de l'exécution via une vtable.

  • Trait Objects - The Rust Programming Language

Commandes différées

Pendant qu'on_event détient un emprunt mutable d'un handler, le réacteur ne peut pas être muté simultanément (le vérificateur d'emprunts de Rust l'impose). Ajouter ou supprimer un autre handler à l'intérieur d'on_event nécessiterait un second emprunt mutable du réacteur, que le compilateur rejette.

La solution : les handlers ajoutent des commandes à un ReactorContext que le réacteur traite après la fin du dispatch courant.

sequenceDiagram
    participant Reactor
    participant Handler
    participant Ctx as ReactorContext

    Reactor->>Handler: on_event(event, &mut ctx)
    Handler->>Ctx: ctx.register(new_handler)
    Handler->>Ctx: ctx.remove(old_token)
    Handler-->>Reactor: Ok(())
    Note over Reactor: dispatch terminé
    Reactor->>Reactor: appliquer les commandes différées
    Reactor->>Reactor: nouveau handler enregistré
    Reactor->>Reactor: ancien handler supprimé

Ce patron est une forme de file de commandes : les mutations structurelles sont exprimées comme des données, différées jusqu'à ce qu'il soit sûr de les appliquer. C'est à la fois une solution aux règles d'emprunt Rust et un principe de conception : le dispatch du handler est stable au sein d'une itération de la boucle d'événements.

Cycle de vie TCP

stateDiagram-v2
    [*] --> Listening: TcpListener lié au port
    Listening --> Accepting: POLLIN sur le fd du listener
    Accepting --> Connected: accept() réussit, WELCOME\n mis en file
    Connected --> ReadWrite: file de réponses non vide
    ReadWrite --> Read: file de réponses vidée
    Read --> ReadWrite: l'app appelle reactor.send()
    Connected --> Disconnected: EOF / POLLERR / tampon > 4096 o
    ReadWrite --> Disconnected: EOF / POLLERR
    Disconnected --> [*]: Client supprimé, fd fermé (RAII)

Découpage en lignes

TCP est un flux d'octets. Un appel read peut livrer la moitié d'une commande, une commande entière, ou plusieurs commandes concaténées. Chaque Client accumule les octets dans un tampon request: Vec<u8> et appelle next_command après chaque lecture pour extraire les lignes complètes :

read #1: b"forw"
tampon : b"forw"              -> pas de ligne complète

read #2: b"ard\nleft\ninv"
tampon : b"forward\nleft\ninv"
  -> émettre "forward"
  -> émettre "left"
restant : b"inv"

Les fins de ligne Unix (\n) et DOS (\r\n) sont acceptées. Les octets de commande sont transmis à app.rs comme Vec<u8> bruts sans conversion UTF-8 ; les parseurs de protocole décident indépendamment si du texte valide est requis.

Le tampon de requête est plafonné à 4096 octets. Dépasser cette limite avant que le tampon ne se vide déconnecte le client, bornant l'utilisation mémoire pour les connexions mal configurées ou malveillantes.

RAII et nettoyage des sockets

Le modèle de possession de Rust fournit RAII (Resource Acquisition Is Initialization) gratuitement. Un Client possède son TcpStream. Lorsque le Client est supprimé de la HashMap du réacteur, l'implémentation de Drop ferme le descripteur de fichier automatiquement. Aucun appel explicite à close n'est nécessaire, et aucun socket ne peut fuir.

Planification des ticks de jeu

Le réacteur utilise le paramètre timeout de poll pour implémenter les ticks de jeu sans second thread. Après chaque itération de la boucle d'événements, il calcule le temps restant jusqu'au prochain tick et le passe comme timeout de poll :

poll(fds, timeout_ms = millis_jusqu_au_prochain_tick)
  • Si un événement réseau arrive en premier, poll retourne avant la fin du timeout. Le réacteur traite l'événement puis boucle avec un timeout plus court.
  • Si la deadline du tick arrive en premier, poll expire. Le réacteur appelle le callback de tick, avance le World et boucle.

Si le serveur prend du retard, il exécute les ticks manquants dans une boucle de rattrapage plafonnée à 50 par itération. Cela empêche un serveur très en retard d'affamer les E/S réseau.

flowchart LR
    A["Calculer timeout<br/>= prochain_tick - maintenant"] --> B["poll(fds, timeout)"]
    B -->|"E/S prête"| C["Dispatcher les handlers"]
    B -->|"Timeout"| D["Exécuter les ticks de jeu<br/>(plafond à 50)"]
    C --> A
    D --> A
