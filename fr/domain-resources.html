Tuiles et ressources

Sources : server/src/world/resource.rs, server/src/world/tile.rs, server/src/world/resource_spawner.rs

Types de ressources

#![allow(unused)]
fn main() {
#[derive(Debug, Clone, Copy, PartialEq)]
pub enum ResourceKind {
    Food, Linemate, Deraumere, Sibur, Mendiane, Phiras, Thystame,
}
}

Copy est dérivé car l'enum n'a pas de champs alloués sur le tas ; passer par valeur est moins coûteux que passer une référence pour un type d'1 octet.

ResourceKind était initialement défini dans la couche protocole aux côtés de son encodage d'index réseau. Il a été déplacé dans world/resource.rs pour que la direction des dépendances soit correcte : la couche protocole importe du domaine, jamais l'inverse.

Struct Resources

#![allow(unused)]
fn main() {
#[derive(Debug, Default, Clone, PartialEq)]
pub struct Resources {
    pub food: u32,
    pub linemate: u32,
    pub deraumere: u32,
    pub sibur: u32,
    pub mendiane: u32,
    pub phiras: u32,
    pub thystame: u32,
}
}

Resources est utilisé à la fois pour le contenu des tuiles (ce qui se trouve au sol) et les inventaires des joueurs (ce qu'un drone transporte). Default donne tout-zéro, l'état initial correct pour une tuile vide ou un joueur fraîchement créé.

Méthodes

MéthodeSignatureObjectif
get(&self, kind) -> u32Lire un champ
add(&mut self, kind, amount)Incrémenter un champ
take(&mut self, kind, amount) -> Result<(), TileError>Décrémenter ; erreur si insuffisant
has_enough(&self, required: &Resources) -> boolVérifier tous les champs
consume(&mut self, other: &Resources)Soustraire tous les champs (précondition : has_enough)

take atomique

take est atomique : si la quantité disponible est inférieure à amount, le champ n'est pas modifié et l'erreur porte le contexte nécessaire pour journaliser ou répondre sans second lookup :

#![allow(unused)]
fn main() {
pub enum TileError {
    InsufficientResource { kind: ResourceKind, available: u32, needed: u32 },
}
}

C'est l'application au niveau domaine de Parse, Don't Validate : l'appelant reçoit une valeur qui explique l'échec, pas un booléen qui force une nouvelle vérification.

consume avec précondition

consume soustrait champ par champ sans vérifier. Il est conçu pour être appelé après que has_enough a confirmé la validité :

#![allow(unused)]
fn main() {
// Séquence de fin d'incantation :
if tile.resources.has_enough(&required) {
    tile.resources.consume(&required);  // sûr : has_enough l'a déjà confirmé
}
}

Les builds de débogage Rust détectent les débordements arithmétiques comme des panics, rendant le mauvais usage immédiatement visible pendant le développement.

Tile

#![allow(unused)]
fn main() {
#[derive(Debug, Default)]
pub struct Tile {
    pub resources: Resources,
    pub players: Vec<u32>,  // ids des joueurs présents ici
}
}

Plusieurs joueurs peuvent partager une tuile ; la spécification indique que les Trantorisés "croisent facilement leurs congénères". Default produit une tuile vide.

Générateur de ressources

Source : server/src/world/resource_spawner.rs

Table de densité

ResourceKindDensitéExemple : carte 10x10
Food0,550
Linemate0,330
Deraumere0,1515
Sibur0,110
Mendiane0,110
Phiras0,088
Thystame0,055

Formule : max(1, floor(largeur * hauteur * densité)). Le minimum de 1 garantit que chaque type de ressource existe toujours sur la carte, même sur une carte 1x1.

Respawn par calcul du déficit

respawn compte le total courant de chaque type en un seul passage sur toutes les tuiles, calcule le déficit et place uniquement les unités manquantes :

flowchart LR
    A["Compter toutes les ressources<br/>sur la carte"] --> B["Calculer le déficit<br/>= cible - courant"]
    B --> C{déficit > 0 ?}
    C -->|oui| D["Placer les unités<br/>manquantes aléatoirement"]
    C -->|non| E["No-op"]
    D --> F["Retourner les positions<br/>de tuiles modifiées"]

Cette conception est idempotente : appeler respawn deux fois quand la carte est pleine ne change rien et retourne une liste vide. Le coût total est proportionnel au déficit, pas à la cible complète.

Générateur congruentiel linéaire

Rng utilise les constantes LCG MMIX de Knuth (multiplicateur 6364136223846793005, incrément 1442695040888963407) avec arithmétique enveloppante u64. Deux générateurs avec la même graine produisent des séquences identiques, rendant les parties reproductibles.

Les 32 bits supérieurs de chaque étape sont utilisés pour next_below afin d'exploiter les meilleures propriétés statistiques des bits de poids fort dans un LCG (les bits de poids faible dans un LCG standard ont des périodes plus courtes).

Références :

  • Linear congruential generator - Wikipedia
  • Knuth, The Art of Computer Programming Vol. 2, section 3.3.4

Service de domaine : take_resource / drop_resource

take_resource et drop_resource opèrent chacun sur une Tile et un Player simultanément. Placer cette logique sur l'un ou l'autre type créerait une importation dans le mauvais sens. Les fonctions libres sont le bon choix pour les opérations qui "n'appartiennent pas naturellement à un seul type" :

#![allow(unused)]
fn main() {
take_resource(&mut tile, &mut player, kind)?;  // tuile -> joueur
drop_resource(&mut tile, &mut player, kind)?;  // joueur -> tuile
}

Les deux délèguent à Resources::take et Resources::add, préservant l'atomicité en cas d'échec.
