Zappy Serveur

Notifications GUI

Sources : server/src/protocol/gui/notification.rs, server/src/protocol/gui/format/

Le sérialiseur est la moitié sortante du protocole GUI. Là où le parseur convertit des octets en commandes typées, le sérialiseur convertit des notifications typées en chaînes réseau.

La fonction format

#![allow(unused)]
fn main() {
pub fn format(notification: &GuiNotification) -> String
}

Une fonction pure : la même entrée produit toujours la même sortie. Pas d'état, pas d'E/S. Le type de retour est String (jamais Result) car la sérialisation de données bien typées ne peut pas échouer.

#![allow(unused)]
fn main() {
let line = format(&GuiNotification::MapSize { width: 10, height: 20 });
assert_eq!(line, "msz 10 20\n");
}

Patrons de conception

Fonction pure

La fonction format n'a aucun effet de bord observable. C'est l'exemple canonique d'un composant de noyau fonctionnel : pour une notification typée donnée, elle retourne toujours la même chaîne. Les tests ne nécessitent ni mocks, ni préparation, ni nettoyage.

Si une mauvaise chaîne atteint un client GUI, toute la chaîne d'appel se réduit à un appel de fonction et une valeur d'entrée. Le débogage est trivialement délimité.

Référence : Functional Core, Imperative Shell - Gary Bernhardt (2012)

Dispatch exhaustif

Le match de Rust sur GuiNotification doit couvrir chaque variante. Ajouter un nouveau type de notification à l'enum et oublier d'ajouter le bras de format est une erreur de compilation. Le compilateur agit comme garant d'exhaustivité sur l'ensemble du protocole.

Masquage de l'information via pub(super)

Chaque fonction helper dans format/player.rs et format/world.rs est déclarée pub(super) : visible uniquement par format/mod.rs. Aucun code externe ne peut appeler directement player::player_death(...). Les détails du format réseau (entiers d'orientation, indices de ressources, préfixe #) sont des décisions internes cachées derrière la seule fonction publique format().

Si le protocole change l'encodage d'orientation de 1-4 vers des lettres cardinales, seul format/player.rs::orientation_code change. Tous les appelants restent intacts.

Référence : On the criteria to be used in decomposing systems into modules - David Parnas (1972)

Éviter les chaînes typées en dur

Le moteur de jeu construit une GuiNotification::PlayerPosition typée avec un PlayerId, une paire u32 x/y et un enum Orientation. Il ne construit jamais directement une chaîne "ppo #1 3 4 2\n". L'encodage des valeurs du domaine vers les entiers réseau se fait en un seul endroit et n'est jamais dupliqué.

C'est le complément côté sortie de Parse, Don't Validate : Format, Don't Encode.

Construction incrémentale de chaîne (IncantationStart)

IncantationStart porte une liste de longueur variable d'identifiants de joueurs participants. Plutôt que de collecter les ids dans un Vec<String> intermédiaire et de les joindre, le helper ajoute chaque id directement au tampon de sortie avec push_str :

#![allow(unused)]
fn main() {
let mut output = format!("pic {} {} {}", x, y, level);
for player in players {
    output.push(' ');
    output.push('#');
    output.push_str(&player.0.to_string());
}
output.push('\n');
}

Une seule allocation de String croît en place au lieu de créer et jeter plusieurs chaînes intermédiaires. C'est la même approche que StringBuilder en Java ou strings.Builder en Go.

Référence : Effective String Handling in Rust - LogRocket Blog
