Zappy Server

The Reactor

The network layer is a single-threaded, non-blocking TCP event loop. It handles many concurrent clients without creating one thread per connection, frames newline-delimited commands, buffers response bytes, and drives the game clock.

Source: server/src/network/

The reactor pattern

The Reactor pattern was formally described by Douglas Schmidt in 1995. Its core insight: rather than giving each I/O source its own thread, register all sources with a single demultiplexer and let it call the right handler when a source is ready.

flowchart TD
    A["Register handlers<br/>(Listener + Clients)"] --> B
    B["poll(fds, timeout)"] --> C{Ready?}
    C -->|"readable/writable"| D["Handler::on_event()"]
    C -->|"timeout"| E["Run game ticks"]
    D --> F["Apply deferred<br/>register/remove/stop"]
    F --> B
    E --> B

The reactor never blocks waiting for one specific client. If client A is slow, clients B and C continue to be served. This is the fundamental advantage over a thread-per-client model for a game server with many idle spectators.

References:

  • Reactor: An Object Behavioral Pattern -- Douglas Schmidt (1995)
  • Reactor Pattern -- Wikipedia
  • Understanding the Reactor Pattern -- DZone

Why poll(2) and not epoll or kqueue?

libc::poll receives an array of pollfd structures and returns which descriptors are ready. It scans all descriptors linearly, so latency grows with the number of connected clients (O(n)). epoll (Linux) and kqueue (BSD/macOS) avoid this by maintaining a kernel-side ready list (O(1) per event).

For a Zappy server with tens to low hundreds of clients, the linear scan is immaterial. poll is POSIX-standard, has a simpler API, and requires no platform-specific abstraction layer. The choice is deliberate: simplicity over premature scalability.

References:

  • poll(2) -- Linux man pages
  • Comparing poll vs epoll -- Cloudflare Blog

Key types

Token

#![allow(unused)]
fn main() {
pub struct Token(pub usize);
}

A Token is the reactor's stable application-level identifier for a handler. File descriptors are not used as identities because the OS may reuse a file descriptor number after a socket is closed. Tokens increase monotonically and are never reused, making stale references safe to detect.

This is an instance of the Newtype pattern: a usize wearing a distinct type so the compiler rejects passing a player id or tile coordinate in its place.

Interest

#![allow(unused)]
fn main() {
pub enum Interest { Read, Write, ReadWrite }
}

A handler declares which readiness events it wants. A client with nothing to send registers Read only. When bytes are queued for writing, the reactor re-registers it as ReadWrite to also receive POLLOUT events. Returning to Read after the flush prevents a busy loop because TCP sockets are almost always writable.

Handler trait

#![allow(unused)]
fn main() {
pub trait Handler {
    fn fd(&self) -> RawFd;
    fn interest(&self) -> Interest;
    fn on_event(&mut self, event: Event, ctx: &mut ReactorContext) -> io::Result<()>;
    // optional capabilities with default no-op implementations:
    fn connected_event(&self, _token: Token) -> Option<NetworkEvent> { None }
    fn disconnected_event(&self, _token: Token) -> Option<NetworkEvent> { None }
    fn add_res_buf(&mut self, _data: &[u8]) -> bool { false }
    fn flush(&mut self) -> NetworkResult<()> { Ok(()) }
}
}

flush is called by Reactor::flush_and_close to drain the write buffer to the socket before the handler is deregistered. This ensures queued response bytes reach the client even when the connection is closed immediately after sending (e.g., when a team has no available slots). Client implements flush by calling write_res_socket() synchronously; other handlers use the default no-op.

The Handler trait decouples the reactor from TCP-specific logic. A TcpListener, a Client, or a future timer pipe all slot into the same collection. Handlers are stored as Box<dyn Handler>, a Rust trait object: different concrete types share one HashMap, with the correct on_event selected at runtime via a vtable.

References:

  • Trait Objects -- The Rust Programming Language

Deferred commands

While on_event holds a mutable borrow of a handler, the reactor cannot be mutated simultaneously (Rust's borrow checker enforces this). Adding or removing another handler inside on_event would require a second mutable borrow of the reactor, which the compiler rejects.

The solution: handlers append commands to a ReactorContext that the reactor processes after the current dispatch completes.

sequenceDiagram
    participant Reactor
    participant Handler
    participant Ctx as ReactorContext

    Reactor->>Handler: on_event(event, &mut ctx)
    Handler->>Ctx: ctx.register(new_handler)
    Handler->>Ctx: ctx.remove(old_token)
    Handler-->>Reactor: Ok(())
    Note over Reactor: dispatch complete
    Reactor->>Reactor: apply deferred commands
    Reactor->>Reactor: new handler registered
    Reactor->>Reactor: old handler removed

This pattern is a form of command queue: structural mutations are expressed as data, deferred until safe to apply. It is both a Rust borrowing solution and a design principle: handler dispatch is stable within an event-loop iteration.

TCP lifecycle

stateDiagram-v2
    [*] --> Listening: TcpListener bound to port
    Listening --> Accepting: POLLIN on listener fd
    Accepting --> Connected: accept() succeeds, WELCOME\n queued
    Connected --> ReadWrite: response queue non-empty
    ReadWrite --> Read: response queue flushed
    Read --> ReadWrite: app calls reactor.send()
    Connected --> Disconnected: EOF / POLLERR / buffer > 4096B
    ReadWrite --> Disconnected: EOF / POLLERR
    Disconnected --> [*]: Client dropped, fd closed (RAII)

Line framing

TCP is a byte stream. One read call may deliver half a command, one command, or multiple commands concatenated. Each Client accumulates bytes in a request: Vec<u8> buffer and calls next_command after each read to extract complete lines:

read #1: b"forw"
buffer:  b"forw"              -> no complete line

read #2: b"ard\nleft\ninv"
buffer:  b"forward\nleft\ninv"
  -> emit "forward"
  -> emit "left"
remaining: b"inv"

Both Unix (\n) and DOS (\r\n) line endings are accepted. Command bytes are forwarded to app.rs as raw Vec<u8> without UTF-8 conversion; the protocol parsers decide independently whether valid text is required.

The request buffer is capped at 4096 bytes. Exceeding this limit before the buffer drains disconnects the client, bounding memory use for misbehaving or hostile connections.

RAII and socket cleanup

Rust's ownership model provides RAII (Resource Acquisition Is Initialization) for free. A Client owns its TcpStream. When the Client is removed from the reactor's HashMap, the Drop implementation closes the file descriptor automatically. No explicit close call is required, and no socket can leak.

  • RAII -- Rust By Example

Game tick scheduling

The reactor uses poll's timeout parameter to implement game ticks without a second thread. After each event-loop iteration, it computes the time remaining until the next tick and passes it as the poll timeout:

poll(fds, timeout_ms = millis_until_next_tick)
  • If a network event arrives first, poll returns early. The reactor processes the event, then loops back with a shorter timeout.
  • If the tick deadline arrives first, poll times out. The reactor calls the game tick callback, advances the World, and loops back.

If the server falls behind, it executes missed ticks in a catch-up loop capped at 50 per iteration. This prevents a severely late server from starving network I/O.

flowchart LR
    A["Compute timeout<br/>= next_tick - now"] --> B["poll(fds, timeout)"]
    B -->|"I/O ready"| C["Dispatch handlers"]
    B -->|"Timeout"| D["Run game ticks<br/>(capped at 50)"]
    C --> A
    D --> A
