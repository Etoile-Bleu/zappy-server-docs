Zappy Server

CLI Arguments

Source: server/src/cli/

The cli module parses raw command-line arguments into a typed ServerArgs. It does not touch sockets, game state, or time. Once ServerArgs is in hand, no argument string is ever read again.

Usage

zappy_server -p port -x width -y height -n name1 name2 ... -c clientsNb -f freq

Flag reference

FlagTypeConstraintDescription
-p portu16any valid portPort the server listens on
-x widthu32>= 1Map width in tiles
-y heightu32>= 1Map height in tiles
-n names...Vec<String>at least oneTeam names (space-separated)
-c clientsNbu32>= 1Maximum clients per team
-f frequ32>= 1Time units per second

Flags may appear in any order. A flag given twice takes its last value (last write wins), consistent with standard Unix CLI behavior.

ServerArgs

#![allow(unused)]
fn main() {
pub struct ServerArgs {
    pub port: u16,
    pub width: u32,
    pub height: u32,
    pub team_names: Vec<String>,
    pub clients_per_team: u32,
    pub freq: u32,
}
}

Every field is the smallest type that naturally rejects out-of-range values. port is u16 (0-65535 by the type; 99999 cannot be stored). The Vec<String> for team names is guaranteed non-empty before ServerArgs is constructed.

Design patterns

Parse, don't validate

The game engine never touches a raw argument string. It receives a ServerArgs with typed fields. The single parse boundary is ServerArgs::from_args(). Everything that crosses it is either a fully typed struct or a typed ArgsError.

Reference: Parse, don't validate -- Alexis King (2019)

Predictive token scan (LL(1))

Arguments are consumed left-to-right with an index cursor. Each token is examined once: if it starts with -, it is a flag; otherwise it is a value for the current flag. No backtracking. This is the same LL(1) pattern used in the GUI command parser, applied to a flat key-value list.

Generic helper: next_parsed<T>

A single generic function replaces what would otherwise be two identical functions next_u16 and next_u32:

#![allow(unused)]
fn main() {
fn next_parsed<T: FromStr>(flag: &str, args: &[String], idx: &mut usize)
    -> Result<T, ArgsError>
}

The type parameter is inferred from context. The constraint T: FromStr is the minimal and correct bound: the function only needs to call str::parse::<T>().

Reference: std::str::FromStr -- Rust Standard Library

Behavior belongs to its type

from_args is a constructor method on ServerArgs, not a free function:

#![allow(unused)]
fn main() {
let config = ServerArgs::from_args(&raw_args)?;
}

The call site reads as intent. A free function parse_args(&raw_args) says nothing about what it produces. The method form is self-documenting.

Error variants

VariantCause
UnknownFlag(String)A -x token was not a recognized flag
MissingValue(&str)A flag was present but no value followed
InvalidValue { flag, raw }A value could not be parsed as the expected type
MissingFlag(&str)A required flag was absent
NoTeamNames-n was present but no names followed
ZeroValue(&str)A numeric flag resolved to zero

The first error encountered terminates the parse immediately. There is no error accumulation or partial success.

The -n flag

-n is the only variable-length flag. It collects all consecutive tokens that do not start with - as team names. Collection stops at the next flag or at end of input:

# Two team names collected, then -c recognized as the next flag
zappy_server -n red blue -c 2 -p 4242 -x 10 -y 10 -f 100

Team names must not start with -. This matches the spec which treats team names as plain identifiers.
